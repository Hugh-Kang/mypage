# 커뮤니티 논의를 반영한 문제 재정의 + 단계적 AI 에이전트 적용 접근

## 0. 설계 프롬프트

> 너는 커뮤니티 논의에서 받은 다섯 가지 비판 — ①강정석의 "목적 없이 챗봇 만들지 말라" ②공냥이의 "ROI·문제정의부터 검증하라" ③도깨비야의 "이탈 데이터를 역으로 활용하는 아이디어" ④이오/바이오의 "서비스 범위가 불명확하다" ⑤한장현의 "추천은 행동 데이터 문제지 에이전트 문제가 아니다, 골든데이터셋+알고리즘이 우선" — 를 모두 반영해서, "콘텐츠 탐색 마찰" 문제를 처음부터 다시 정의하고, AI 에이전트를 가장 마지막 단계에만 조건부로 배치하는 단계적 접근을 설계하라. 이전 답변들(에이전트 중심 설계)을 방어하는 게 아니라, 비판을 수용해서 접근 자체를 다시 짜라.

## 1. 문제 재정의 — "에이전트가 필요하다"가 아니라 "가설이 맞는지부터"

### 기존 접근 (비판받은 지점)
"콘텐츠를 못 골라 탐색시간이 길어지고 이탈한다 → 그러니 AI 에이전트로 선제적 추천을 해주자"는, **해법(에이전트)을 먼저 정해놓고 문제를 거기에 끼워 맞춘** 접근이었습니다. 강정석("목적 없이 챗봇 만들지 말라")과 공냥이("문제정의부터 이상하다")의 지적이 정확히 이 지점을 겨냥합니다.

### 재정의된 문제
해법을 배제하고 다시 쓰면, 진짜 목표는 "AI 에이전트를 만드는 것"이 아니라 **"구독 해지율을 낮추고 시청 시간·광고 수익을 늘리는 것"**입니다. "탐색 마찰이 길어서 이탈한다"는 건 아직 **검증 안 된 가설**일 뿐이고, 이 가설이 실제로 해지율과 연결되는지조차 모르는 상태에서 에이전트를 설계하는 건 순서가 잘못됐습니다.

## 2. 단계적 접근 — 5단계 (에이전트는 조건부로 가장 마지막에)

| 단계 | 내용 | 통과 조건 (다음 단계로 넘어갈 근거) |
|---|---|---|
| **0단계. 가설 검증** | 탐색시간이 길다가 이탈한 사용자군과 아닌 사용자군의 **이후 구독 해지율을 코호트로 비교**해서, 문제정의 자체가 맞는지부터 확인 | 두 그룹 간 해지율 차이가 통계적으로 유의미해야만 다음 단계로 진행 |
| **1단계. 기존 알고리즘 먼저 개선 (한장현 반영)** | LLM·에이전트 없이, 기존 추천 알고리즘에 "탐색은 길지만 아직 선택 안 한 사용자"라는 행동 이벤트 신호를 새로 추가해서 랭킹만 보강 | 이 개선만으로 체류시간·완료율이 충분히 좋아지면 **여기서 끝** — 에이전트로 갈 필요 없음 |
| **2단계. 최소 비용 실험 (공냥이 반영)** | 1단계로도 부족하면, 전체 LLM 시스템을 만들기 전에 사람이 직접 큐레이션하는 대화형 추천(Wizard-of-Oz)으로 소규모 A/B 테스트 | 기존 알고리즘 대비 통계적으로 유의미하게 더 나은 결과가 나와야만 진행 |
| **3단계. RAG 챗봇 (자율성 최소)** | 2단계가 검증되면, 검색이라는 도구 하나만 쓰는 RAG 챗봇으로 시작 — 검색 대상은 기존 추천 알고리즘의 결과 그 자체 | 자율적 다단계 작업(실행)이 실제로 필요하다는 근거가 쌓여야만 다음 단계 고려 |
| **4단계. 에이전트로 확장(조건부)** | 찜 등록·알림 설정처럼 실행까지 필요하다는 근거가 쌓였을 때만, 그 범위 안에서 도구 호출·검증 루프를 갖춘 에이전트로 확장 | — |

**핵심**: 에이전트는 "처음부터 만드는 목표"가 아니라 **"0~3단계를 다 거치고도 남는, 검증된 필요에만 조건부로 쓰는 마지막 수단"**입니다.

## 3. 범위 한정 (이오/바이오 반영)

"다양한 OTT 서비스를 넘나드는 상위 레이어"는 제가 티빙 PM으로서 다룰 범위도 아니고, 처음부터 복잡도만 키워 검증을 어렵게 만듭니다. **티빙 단일 서비스 안에서, 티빙이 이미 가진 데이터·알고리즘 자산을 재사용하는 것**으로 범위를 명확히 한정하겠습니다.

## 4. 도깨비야 아이디어의 재배치

"이탈·해지 고객이 원했던 콘텐츠를 역으로 분석해서 회사에 제안"하는 아이디어는 좋지만, 이것도 사용자 대상 에이전트가 아니라 **콘텐츠 전략팀을 위한 내부 데이터 분석 리포트 자동화**로 재배치하는 게 맞습니다(한장현 논리와 동일 — 이것도 본질은 행동 데이터 분석이지 에이전트가 필요한 문제가 아님).

## 5. 면접용 통합 답변

> "말씀하신 지적을 반영해서 다시 접근하겠습니다. 먼저 '에이전트를 만들자'가 아니라, 탐색 마찰이 실제로 구독 해지와 연결되는지부터 기존 데이터로 코호트 비교해 검증하겠습니다. 이게 확인되더라도, 바로 에이전트로 가지 않고 먼저 기존 추천 알고리즘에 행동 신호를 추가하는 것만으로 해결되는지 봅니다. 그걸로 부족하면, 전체 시스템을 만들기 전에 사람이 직접 큐레이션하는 최소 실험으로 기존 알고리즘 대비 효과를 검증하고요. 여기까지 다 통과해야 비로소 검색 도구 하나만 쓰는 RAG 챗봇으로 시작하고, 찜 등록이나 알림처럼 실행이 필요하다는 근거가 추가로 쌓였을 때만 에이전트로 확장하겠습니다. 범위도 티빙 단일 서비스로 한정하고, 이탈 고객 분석 같은 아이디어는 사용자용 에이전트가 아니라 내부 콘텐츠 전략팀을 위한 데이터 분석 자동화로 따로 가져가겠습니다. 결국 에이전트는 이 모든 단계를 거치고도 남는, 검증된 필요에만 쓰는 마지막 수단이라고 생각합니다."

## 6. 1분 스피치 압축 버전 (실제 발화용)

> "말씀하신 지적에 전적으로 동의합니다. 그래서 저라면 '에이전트부터 만들자'가 아니라, 탐색 마찰이 정말 구독 해지로 이어지는지 기존 데이터로 먼저 검증하겠습니다. 그다음엔 LLM 없이 기존 추천 알고리즘에 행동 신호 하나만 추가해서 해결되는지 보고, 부족하면 사람이 직접 큐레이션하는 최소 실험으로 기존 알고리즘과 비교 검증하겠습니다. 이 단계들을 통과해야 비로소 검색 도구 하나만 쓰는 RAG 챗봇으로 시작하고, 실행까지 필요하다는 근거가 쌓였을 때만 에이전트로 확장하겠습니다. 범위도 티빙 단일 서비스로 한정하고요. 결국 에이전트는 모든 단계를 거치고도 남는, 검증된 필요에만 쓰는 마지막 수단이라고 생각합니다."
