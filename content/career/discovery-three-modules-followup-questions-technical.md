## 0. 설계 프롬프트

> 너는 Discovery 3개 모듈 답변 각각에 대해, 면접관이 "그래서 구체적으로 어떻게 구현할 건데?"라고 파고들 때 나올 법한 꼬리질문을 모듈별로 3개씩 예상하는 면접 코치다. 단순 개념 설명이 아니라 실제 기술적 구현 방식(아키텍처, 알고리즘, 데이터 구조)까지 포함한 답변을 준비하라. 확인되지 않은 티빙 내부 사실은 단정하지 말고 일반적으로 알려진 방법론으로 제시하라.

## 1. 모듈 ① 메인홈 / AI 챗봇 에이전트

### 꼬리질문 1-1. "RAG 기반 챗봇을 만든다고 했는데, 구체적으로 어떤 기술 스택과 파이프라인으로 구현할 건가요?"

**예상답변**: "콘텐츠 메타데이터(제목·배우·장르·줄거리·태그)를 벡터DB에 임베딩해두고, 사용자 질의가 들어오면 같은 임베딩 모델로 질의를 벡터화해 유사도 검색으로 후보를 가져온 다음, 그 후보를 LLM에 컨텍스트로 넣어 자연어 답변을 생성하는 구조로 구현하겠습니다. 다만 배우·장르처럼 정확히 일치해야 하는 조건은 벡터 유사도만으론 놓칠 수 있어서, 메타데이터 필터링(정확 매칭)과 벡터 검색(의미 매칭)을 함께 쓰는 하이브리드 검색으로 설계하겠습니다. 예를 들어 '이 배우 나온 다른 작품'은 배우명 필터로 정확히 걸러낸 뒤, '비슷한 분위기'처럼 모호한 질의에만 벡터 유사도를 쓰는 식입니다."

### 꼬리질문 1-2. "'검색 성공률'이라는 지표, 정확히 어떻게 정의하고 측정할 건가요?"

**예상답변**: "검색 성공률은 '검색 후 추가 행동 없이 바로 원하는 결과에 도달했는가'로 정의하고 싶습니다. 구체적으로는 검색 결과 클릭률뿐 아니라, 같은 세션 내 재검색(쿼리 재입력) 비율과 '결과 없음' 응답 비율을 함께 보겠습니다. 검색 성공 = 검색 후 N초 이내 클릭 발생 AND 같은 세션에서 재검색 없음, 이렇게 정의하면 단순 클릭률보다 '한 번에 원하는 걸 찾았는가'를 더 정확히 포착할 수 있습니다. 로깅 설계는 세션ID·쿼리·응답결과수·클릭여부·재검색여부를 이벤트 단위로 쌓아서 검색 퍼널을 추적하는 구조가 되겠습니다."

### 꼬리질문 1-3. "2단계(다중 턴 챗봇)에서 3단계(에이전트)로 넘어가는 기준은 뭔가요? 그리고 에이전트가 실패하면 어떻게 복구하나요?"

**예상답변**: "넘어가는 기준은 2단계에서 수집한 데이터로 판단하겠습니다. 구체적으로 '사용자가 여러 턴에 걸쳐 좁혀나갔는데도 끝내 만족스러운 결과를 못 찾고 이탈한 비율'이 일정 수준 이상이면, 단순 대화형 좁히기로는 한계가 있다는 신호로 보고 에이전트 단계 검토를 시작하겠습니다. 에이전트의 실패복구는, 도구 호출 결과가 비어있거나 사용자가 연속으로 '아니요/별로'라고 반응하면 같은 방식을 반복하지 않고 다른 검색 전략(예: 장르 대신 분위기 태그로 재시도)으로 전환하게 하고, 그래도 실패하면 사람이 큐레이션한 기본 추천으로 안전하게 폴백(fallback)하는 구조로 설계하겠습니다."

## 2. 모듈 ② 검색 / 추천 / Push / 배너 / Growth

### 꼬리질문 2-1. "시청완료율·이탈지점 같은 행동 신호를, 기존 추천 알고리즘에 기술적으로 어떻게 결합할 건가요?"

**예상답변**: "기존 추천 모델이 협업 필터링 기반이라고 가정하면, 입력 피처에 암묵적 피드백(implicit feedback)을 추가하는 방식으로 결합하겠습니다. 예를 들어 '시청완료율'은 단순 클릭(0/1)보다 더 세밀한 가중치(완료율 0~1)로 바꿔서 사용자-콘텐츠 상호작용 행렬에 반영하고, '중도 이탈 지점'은 부정 신호로 변환해 같은 행렬에 음수 가중치나 별도 피처로 넣겠습니다. 모델 구조 차원에서는, 기존이 행렬분해(matrix factorization) 계열이면 피처를 더 유연하게 받을 수 있는 two-tower 임베딩 모델로 점진적으로 전환하는 것도 고려하겠지만, 처음부터 모델을 바꾸기보다 기존 모델에 피처만 추가해 효과를 먼저 검증하는 순서로 가겠습니다."

### 꼬리질문 2-2. "콜드스타트 콘텐츠는 행동 데이터가 없는데, 메타데이터 유사도 기반 추천을 구체적으로 어떻게 구현하나요?"

**예상답변**: "신작의 메타데이터(장르·줄거리·배우·키워드)를 텍스트 임베딩 모델로 벡터화하고, 이미 행동 데이터가 쌓인 기존 콘텐츠들의 벡터와 코사인 유사도를 계산해서 가장 가까운 기존 콘텐츠들을 찾습니다. 그다음 그 기존 콘텐츠들을 선호했던 사용자군의 상호작용 패턴을 신작에 '빌려와서' 초기 추천 후보에 포함시키는 방식입니다. 즉 신작 자체의 행동 데이터가 없어도, '이 신작과 메타데이터가 유사한 작품을 좋아했던 사람들'을 초기 타겟으로 잡는 content-to-collaborative 브리지 구조입니다. 데이터가 쌓이기 시작하면 이 메타데이터 기반 가중치는 점점 줄이고 실제 행동 데이터 기반 가중치로 자연스럽게 전환하겠습니다."

### 꼬리질문 2-3. "롱테일 노출을 늘리면 CTR·CVR이 떨어질 수 있다고 했는데, 가드레일은 구체적으로 어떤 지표를 어떤 임계치로 모니터링할 건가요?"

**예상답변**: "핵심 가드레일은 전체 세션 단위의 이탈률과 체류시간입니다. 롱테일 콘텐츠 비율을 늘리는 실험을 할 때, 개별 콘텐츠의 CTR이 아니라 '그 세션에서 사용자가 결국 뭔가를 시청했는가'와 '체류시간이 기존 대비 줄지 않았는가'를 기준으로 보겠습니다. 구체적으로는 A/B 테스트로 롱테일 비율을 예를 들어 10%→20%로 올린 그룹과 기존 그룹을 비교해서, 세션 이탈률이 사전에 정한 허용 범위(예: 상대적으로 5% 이상 악화) 밖으로 나가면 비율을 다시 낮추는 자동 롤백 조건을 플랫폼에 걸어두는 방식으로 설계하겠습니다. 즉 '커버리지는 늘리되, 이탈률이라는 하한선은 넘지 않는다'는 제약 조건 안에서 점진적으로 비율을 조정하는 구조입니다."

## 3. 모듈 ③ A/B Test Platform, 커뮤니케이션·메시지

### 꼬리질문 3-1. "무작위 배정과 실험 간 트래픽 격리를 플랫폼이 '자동 보장'한다고 했는데, 기술적으로 어떻게 구현하나요?"

**예상답변**: "무작위 배정은 사용자ID와 실험ID를 합쳐 해시값을 만들고, 그 해시값을 버킷(예: 0~99) 중 하나로 매핑하는 결정론적 해싱(consistent hashing) 방식으로 구현하겠습니다. 이렇게 하면 같은 사용자는 같은 실험에서 항상 같은 그룹에 배정되면서도, 실험ID가 다르면 해시 결과도 달라져서 서로 다른 실험끼리는 독립적인 무작위성을 가지게 됩니다. 트래픽 격리는 여러 실험을 '레이어(layer)'라는 독립된 네임스페이스로 나눠서, 같은 사용자가 레이어 A의 썸네일 실험과 레이어 B의 추천 알고리즘 실험에 동시에 들어가도 서로 간섭하지 않게 하는 구조(직교 실험 설계)로 만들겠습니다. 같은 레이어 안에서는 한 사용자가 동시에 여러 실험에 들어가지 않도록 배타적으로 관리하고요."

### 꼬리질문 3-2. "실험 결과가 통계적으로 유의미한지는 어떻게 자동으로 판정할 건가요? 중간에 결과 보고 조기 종료하면 안 되는 이유는요?"

**예상답변**: "실험 시작 전에 최소 샘플 사이즈를 검정력 분석(power analysis)으로 미리 계산해서, 그 샘플이 다 모일 때까지는 결과를 공식적으로 판정하지 않는 고정 기간(fixed-horizon) 방식을 기본으로 하겠습니다. 중간에 결과를 보고 유의미해 보이는 시점에 조기 종료하면, 여러 번 반복 검정하는 효과 때문에 실제로는 유의미하지 않은데 유의미하다고 잘못 판단할 확률(false positive)이 크게 올라가기 때문입니다. 다만 실무에서는 빨리 확인하고 싶은 니즈가 있어서, 필요하다면 유의수준을 중간 체크 횟수에 맞게 보정하는 순차 검정(sequential testing) 방식을 플랫폼에 옵션으로 추가하는 것도 고려하겠습니다. 기본 판정은 카이제곱 검정이나 비율 차이에 대한 z-검정으로 p값을 자동 계산하고, 유의수준(예: 0.05)과 최소 샘플 충족 여부를 함께 만족해야 '유의미'로 표시되게 하겠습니다."

### 꼬리질문 3-3. "메시지 피로도 가드레일, 구체적으로 어떤 규칙으로 발송을 제한할 건가요?"

**예상답변**: "사용자 단위로 최근 N일 내 수신한 푸시/메시지 횟수를 누적 카운트해두고, 일정 횟수(예: 하루 2건, 주 5건) 상한을 넘으면 우선순위가 낮은 메시지는 발송 큐에서 보류하는 규칙 기반 가드레일로 시작하겠습니다. 여기에 더해 수신 거부(옵트아웃)나 알림 차단 행동을 보인 사용자는 즉시 그 채널의 발송 빈도를 자동으로 낮추는 피드백 루프도 넣겠습니다. 처음부터 복잡한 최적화 모델을 쓰기보다, 상한선 규칙으로 먼저 하한을 지키고, 이후 발송 타이밍이나 채널 선택을 개인화하는 건 데이터가 쌓인 다음 단계로 미루겠습니다."

## 4. 종합 — 이 답변들의 공통 설계 원칙

> "세 모듈 모두에서 제가 가져가려는 기술적 원칙은 같습니다. 새 모델을 처음부터 만들기보다 기존 구조에 신호/피처를 추가하는 점진적 접근을 우선하고, 복잡한 최적화보다 명확한 규칙·임계치 기반 가드레일을 먼저 걸어서 리스크를 통제한 다음, 데이터가 쌓이면 더 정교한 방식(순차 검정, 자율 에이전트, 피처 기반 모델 전환)으로 단계적으로 고도화하는 것입니다."
