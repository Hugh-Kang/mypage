# 김희재와의 모의면접 — 질의응답 구조화 및 개선 제안

> 작성 목적: 2026.09.25 김희재와 진행한 Discovery팀 모의면접(약 1시간 26분)의 질의응답을 구조화하고, 각 답변을 어떻게 더 개선할 수 있을지 명확한 근거와 함께 제안
> 근거자료: 사용자가 정리한 질의응답 요약 + Gemini 회의록(타임스탬프 포함)
> 참석자: 강해우(지원자), 김희재(면접관 역할)

## 0. 설계 프롬프트

> 너는 모의면접 코칭 전문가다. 지원자가 친구와 진행한 모의면접의 질의응답 요약본과 Gemini 회의록(타임스탬프 포함)을 대조해서, ① 주제별로 질의응답 흐름을 구조화하고, ② 각 답변이 실제로 얼마나 설득력 있었는지 평가하고, ③ 이전에 함께 정리한 자료(인과관계/표본규모 방어 템플릿, 온톨로지 설명, U+쿠폰 재구조화, Discovery 역할 우선순위)와 실제로 일치하게 답변했는지 대조 검증하고, ④ 불일치하거나 약한 지점은 명확한 근거를 들어 개선안을 제시하라. 특히 포트폴리오 슬라이드의 서술과 인터뷰 답변 내용이 서로 다른 경우, 추측하지 말고 사실관계 확인이 필요하다고 명시하라.

## 1. 모의면접 개요

- 참석자: 강해우(지원자), 김희재(면접관 역할)
- 소요시간: 약 1시간 26분 (김희재 본인의 1차 면접 준비를 위해서도 함께 진행)
- 구성: 자기소개 → 홈화면 추천 프로젝트 심층질의 → 티빙 홈화면 개선 아이디어 브레인스토밍 → 성과/실패 프로젝트 → 팀 적합성 → (휴식 후) 챗봇/온톨로지 심화 논의 → 티빙 최신 이슈 논의

## 2. 최우선 확인 필요 사항 — 사실관계 불일치 가능성

**가장 먼저 짚어야 할 지점입니다.** 인과관계 검증 질문에 대한 답변에서 다음과 같이 말씀하셨습니다.

> "해당 기능은 AB test를 진행해서, 기존 추천 시스템과 개선된 추천시스템을 나눠서 결과를 우선 봤구요. ab test에서도 차이가 나타나서, 전체 사용자 대상으로 확장시켜서 결과를 봤고, 유사한 결과가 나타났습니다." + "충전 빈도, 충전량, 연령대 등도 동일하게 나눠서 샘플링 되게끔 고려"

이건 상당히 엄밀한 **무작위 대조군 A/B 테스트**를 수행했다는 주장입니다. 그런데 포트폴리오 슬라이드(12~13p)에는 이 근거가 **"변경 이전 vs 변경 이후"의 시계열 전후 비교 막대그래프**로만 제시되어 있고, 무작위 그룹 분리나 충전빈도·연령대 등 공변량 통제에 대한 언급은 없습니다. 이전에 함께 정리한 `interview-defense-templates-causality-samplesize.md`에서도 이 프로젝트를 "대조군 없는 전후 비교"로 분류하고 방어 전략을 짰습니다.

**두 가지 가능성이 있습니다.**
1. 실제로 공식 전체 적용 전에 **소규모 A/B 파일럿을 먼저 돌렸고**, 포트폴리오의 "변경 이전/이후" 차트는 그 이후 전체 적용 시점의 비교라서 슬라이드에 A/B 단계가 생략되어 있을 뿐인 경우
2. 모의면접이라는 편안한 자리에서 **더 설득력 있어 보이려고 방법론을 실제보다 강하게 표현**했을 가능성

**둘 중 무엇이 사실인지 반드시 스스로 확인**하고, 실제 면접 전에 답변을 사실에 맞게 통일해야 합니다. 만약 1번(실제 A/B 파일럿이 있었음)이 맞다면 오히려 강점이니 포트폴리오에도 명확히 추가하는 것이 좋고, 2번(전후비교였을 뿐)이라면 실제 면접에서는 "AB test"라는 단어 대신 이전에 준비한 인과관계 방어 골격(완벽한 인과관계 증명은 아니라는 점 인정 → 메커니즘 설명 → 한계 인정 → 다음 단계)을 그대로 써야 합니다. 실제 면접에서 "A/B 테스트를 했다"고 답한 뒤 "그룹은 어떻게 나눴나요", "샘플 크기는요", "왜 그 지표를 1차 지표로 잡았나요" 같은 후속 질문이 들어오면, 사실과 다른 답변은 그 자리에서 바로 무너질 위험이 있습니다.

## 3. 주제별 질의응답 구조화 및 평가

### 3-1. 홈화면 충전구역 추천 프로젝트 (심층 질의)

| 질문 | 답변 요지 | 평가 |
|---|---|---|
| 홈화면 전체를 개편한 건가요? | 아직 전체 개편 전, 최소 공수로 rule-base 추천 규칙만 우선 변경 | **강점.** 이전에 정리한 `home-recommendation-feedback-restructure.md`의 "일부만 먼저 했다를 강점으로 전환" 프레이밍이 그대로 반영됨. 준비한 답변이 실전에서 잘 나온 사례 |
| 데이터는 어떻게 확인하나요? | GA, Superset 대시보드, 사내 챗봇 에이전트에 쿼리문 입력해서 확인 | 구체적 툴 3종을 언급해 실무 신뢰도 있음. 다만 "챗봇 에이전트에 쿼리문을 넣어 확인한다"는 부분은 그 챗봇이 무엇을 하는 챗봇인지(데이터 분석 전용 사내 챗봇) 한 문장 설명이 없으면 생소하게 들릴 수 있음 |
| 인과관계는 어떻게 검증했나요? (AB test 언급) | 위 2번 항목 참고 — **사실관계 확인 필요** | 방법론 자체(대조군, 전체 확장, 재현 확인)는 이상적인 답변 구조이나, 포트폴리오 서술과 불일치 가능성 |
| AB test 편향 방지는? | 충전빈도, 충전량, 연령대 등 공변량 통제해서 샘플링 | 통계적으로 정확한 개념(공변량 균형화)을 정확히 짚었다는 점은 강점. 다만 위와 같은 이유로 실제 근거 자료와 일치하는지 재확인 필요 |

### 3-2. 티빙 홈화면 추천 플로우 설계 제안 (브레인스토밍, 가장 많이 파고든 주제)

이 구간이 이번 모의면접에서 **가장 많은 압박 질문(연속 5개)**을 받은 구간이자, 김희재가 세션 후반에 직접 "챗봇에 대한 이해도나 설명이 유저플로우·데이터·실무 워크플로우 측면에서 다소 아쉬웠다"고 명시적으로 피드백한 지점입니다.

**질문 흐름과 답변**:
1. "홈화면 개선 아이디어는?" → "채팅형 챗봇으로 콘텐츠 추천"
2. "검색과 뭐가 다른가?" → "검색은 명확한 목적 기반, 채팅형은 선제적 제안" (양호)
3. "카테고리 클릭시 채팅형으로 안내하는 거냐?" → "네 그렇게도 할 수 있을 것 같다" (**약함 — 확답 회피성 답변**)
4. "과한 정보 아니냐?" → "너무 과하지 않게 정리해서" (**약함 — 질문을 되풀이한 답변, 구체적 해법 없음**)
5. "영상 끝났을 때 이미 추천이 뜨는데 굳이 챗봇이 또 말해줘야 하나?" → 취향 수집 방안으로 재프레이밍 (**좋은 전환**)

**평가**: 5개 질문 중 3, 4번 답변이 "그렇게도 할 수 있을 것 같다", "과하지 않게 정리해서"처럼 **질문에 되물어온 표현을 살짝 바꿔 되돌려주는 패턴**으로, 새로운 정보 없이 방어만 한 형태입니다. 이건 앞서 정리한 `interview-cross-company-pattern-analysis.md`에서 지적한 "이지선다/압박 질문에서 회피 후 재압박당하는 패턴"과 같은 계열의 약점입니다.

**개선 제안 (근거: 김희재의 실제 사후 피드백 + 세션 후반부에 두 사람이 함께 도출한 더 나은 답)**: 브레인스토밍형 질문을 받으면, 즉흥적으로 아이디어를 던지고 압박 질문에 하나씩 반응하기보다, **처음부터 미니 PRD 형태로 구조화해서 먼저 제시**하는 것이 압박에 덜 흔들립니다.

> "탐색 피로도가 높은 사용자의 문제를 풀고 싶은데, 구조는 이렇게 잡겠습니다. ① 문제: 무엇을 볼지 모르는 사용자의 탐색 시간, ② 트리거: 카테고리 진입 시 패널형 UI 대신 채팅형으로 짧게 취향을 1~2개만 확인, ③ 출력: 장문 설명이 아니라 쇼츠 미리보기 리스트로 즉시 시청 유도, ④ 검색과의 차이: 검색은 목적이 명확할 때, 이건 목적이 불명확한 사용자에게 선제 제안, ⑤ 우려되는 정보 과부하는 선택지를 칩(chip) 형태로 최소화해서 방지하겠습니다."

이 구조(문제-트리거-출력-차별점-리스크 대응)를 먼저 한 번에 제시하면, 이후 압박 질문이 들어와도 "그 부분은 ④에서 이미 설명드린 것처럼..."처럼 이미 답한 것을 참조하며 대응할 수 있어 훨씬 안정적입니다. 실제로 세션 후반부(01:21:19)에 두 사람이 함께 "패널형 UI 대신 채팅형으로 빠르게 취향을 물어보고 쇼츠 리스트로 미리보기 제공"이라는, 정확히 이 구조에 해당하는 답을 도출했습니다 — **이걸 실제 면접에서는 압박받은 뒤 나오는 답이 아니라 처음부터 제시하는 답으로 순서를 바꿀 것**을 권장합니다.

### 3-4. 성과가 좋았던 프로젝트 (U+ 제휴쿠폰)

> "매출 상승이 직접적인 목적은 아니었으나 휴면 회원이 복귀하면서 매출에 기여하게 된 사례를 포트폴리오에 의도와 함께 솔직하게 기재했다" — 김희재: "이러한 솔직한 접근이 타당하다"

**평가**: **강점.** 이전에 정리한 `uplus-coupon-scope-correction.md`에서 제안한 "매출 16% 전체를 성과로 주장하지 말고 휴면 회원 복귀라는 좁고 방어 가능한 기여로 말하라"는 톤 조정이 정확히 반영됐고, 상대방(면접관 역할)에게서도 긍정적 반응을 얻은 사례입니다.

### 3-5. 매출 증대 방안 / 푸시 정책

- 매출: 프로모션(신규 유치) → 구독 요금제(락인), 배달의민족 멤버십 비유 — 무난하나 다소 일반론적. 개선하려면 "왜 락인이 프로모션보다 나은지"를 볼트업 데이터(예: 즐겨찾기 등록자 CTR 5배 차이 데이터)와 연결해서 "락인된 사용자는 이미 재방문 의도가 확인된 세그먼트와 유사하다"는 식으로 본인 프로젝트와 연결하면 더 강력함
- 푸시 정책: 사용자 피로도(텀 관리), 서버 관리(시간대 분산·증설), 운영(콜센터 대응 가능 시간대) 3축 — **강점.** 구체적이고 실무적. 티빙 적용 답변("스우파처럼 관심 콘텐츠 시작 시각에 푸시")도 방향은 맞으나, "개인화된 푸시 타이밍(사용자별 주시청 시간대 학습)"까지 언급하면 Discovery 도메인(Push 모듈)과 더 직접 연결됨

### 3-6. 실패 프로젝트 / 리딩 경험 / 팀 적합성

- 실패 프로젝트(러닝보조기): MVP 우선 출시 → 시장반응 확인 → B2B/B2B2C 전환 — 솔직하고 구조적, 개선 여지 적음
- 리딩 경험: "현재 혼자서 MAU 20만 서비스 전체 기획·운영" — 구체적 수치 있어 좋음
- Discovery 희망 파트: 챗봇+콘텐츠추천, 본인 프로젝트(대화참여도 25%, 건강디저트 A-to-Z, CTR 7%→25%) 근거 제시 — 이전에 정리한 `tving-discovery-role-priority.md`의 1순위 논리와 정확히 일치. 준비한 우선순위 논리가 실전에서 그대로 활용된 좋은 사례
- 설득 경험: "정량 데이터 제시, 없으면 유사서비스 벤치마킹" — 무난하나 `interview-cross-company-pattern-analysis.md`에서 이미 "여러 회사에서 반복된 정형화된 답변"으로 지적한 패턴. 구체적 일화(예: 즐겨찾기 CTR 5배 데이터로 팀장을 설득한 구체적 순간)를 하나 더 붙이면 차별화됨

## 4. 김희재가 제공한 개념 자산 — 본인 것으로 소화해서 재활용할 목록

이번 세션에서 김희재가 직접 설명하거나 제안한 아래 개념들은, 지금은 "상대방의 설명에 동의"하는 수준으로만 소비되었습니다. 실제 면접에서는 이걸 스스로 설명할 수 있어야 하므로, 학습·정리가 필요합니다 (Gemini 회의록의 "다음 단계"에도 동일하게 명시됨).

1. **온톨로지 → 지식그래프 → LLM 연동 흐름**: 클래스/연관관계 정의(스키마) → 회원·콘텐츠 노드와 간선으로 실제 데이터 매핑(지식그래프) → 질의 관련 노드 추출·탐색 → LLM에 전달해 추론. (`chatbot-ontology-vs-vectordb-explanation.md`에 이미 온톨로지 기초 정의는 정리되어 있으니, 이 문서에 "지식그래프 탐색→LLM 전달" 흐름만 추가로 보강하면 됨)
2. **멀티에이전트 라우팅 구조**: 콘텐츠 추천 에이전트 + Q&A 에이전트를 사용자에게는 하나의 챗봇처럼 보이게 하고, 내부적으로 별도 라우팅 에이전트가 적절한 하위 에이전트로 연결
3. **콜드스타트 + 협업 필터링 조합**: 신규 사용자는 인기순 노출로 데이터 확보 → 시청 기록 생기면 유사 콘텐츠·협업 필터링으로 전환
4. **개인화와 다양성의 트레이드오프(세렌디피티)**: 초개인화만 하면 취향 변화·새 장르 발견이 막힘 → 유튜브 알고리즘처럼 주 취향 반영하되 색다른 콘텐츠를 의도적으로 섞는 전략
5. **PM의 홈 화면 레이아웃 설계 사례**: 개인화 배너 10개 + 인기순 10개 + 실시간 차트 10개 = 30개 조합, 4×5·5×6 등 레이아웃별 노출 순서를 PM이 직접 정의하는 실무 사례 — Discovery의 "전체 서비스 구조 설계" 요건과 직접 연결되는 구체적 사례이므로 본인의 언어로 재구성해둘 것

## 5. 종합 액션 아이템

1. **(최우선) 홈화면 추천 프로젝트의 검증 방법(A/B 테스트 vs 전후비교)이 실제로 무엇이었는지 사실 확인** — 확인 후 포트폴리오·인터뷰 답변 표현을 통일
2. 티빙 홈화면 개선 아이디어는 "문제-트리거-출력-차별점-리스크 대응"의 미니 PRD 구조로 먼저 제시하는 연습(압박받고 나서가 아니라 선제적으로)
3. 위 4번 목록(온톨로지 흐름, 멀티에이전트 라우팅, 콜드스타트+협업필터링, 개인화-다양성 트레이드오프, 레이아웃 설계 사례)을 본인 언어로 정리해 능동적으로 설명할 수 있도록 학습
4. 설득 경험 답변에 구체적 일화 1개 추가(정형화된 답변 탈피)
5. 강점으로 확인된 답변(홈화면 프로젝트 배경 설명, U+쿠폰 성과 프레이밍, 온톨로지 솔직 답변, Discovery 희망 파트 근거 제시, 푸시 정책)은 그대로 유지 — 기존 준비 자료가 실전에서 효과를 봤다는 증거
