# 챗봇 vs AI 에이전트 예상 질문 5개 — 커뮤니티 논의 반영 재답변

## 0. 설계 프롬프트

> 너는 커뮤니티 논의(공냥이·강정석·도깨비야·이오바이오·한장현의 비판)를 모두 소화한 뒤, 기존에 답했던 5개 예상 질문에 다시 답하는 지원자다. 이전 답변의 "에이전트를 어떻게 잘 만들지" 프레임을 버리고, "에이전트가 필요한지부터 검증 → 기존 알고리즘 먼저 시도 → 최소 실험 → RAG → 조건부 에이전트"라는 단계적 게이트 프레임으로 모든 답변을 다시 구성하라. 이전 답변과 비교해서 무엇이 달라졌는지도 짧게 짚어라.

## 1. Q&A 재구성

### Q1. 티빙의 현재 시스템과 JD의 '챗봇 에이전트'의 차이를 5가지 기준으로 설명해보세요.

**재답변**: "확인된 사실은 아니지만, 제가 아는 한 티빙은 랭킹 기반 추천 알고리즘이 핵심이고 자율성·도구사용·실패복구가 없는 단계입니다. 이건 챗봇도 아니고, 자동화 스펙트럼에서 챗봇보다도 낮은 위치입니다. JD의 '챗봇 에이전트'는 스스로 도구를 선택하고 여러 단계를 거쳐 결과를 만드는 시스템일 테니, 기획의 핵심은 기존 추천 자동화 위에 자율성·도구사용·실패복구를 새로 얹는 작업이라고 생각합니다. 다만 다섯 기준을 다 갖추는 것 자체가 목표는 아니고, 기존 알고리즘을 행동 데이터로 개선하는 것만으로 충분한 경우도 많아서, 에이전트는 기존 방식으로 안 풀리는 게 검증됐을 때만 쓰는 수단이라고 생각합니다."

**1차 답변과 달라진 점**: 이전엔 "지금 시스템은 자동화 수준이 낮으니 세 축을 얹어야 한다"는 식으로 다섯 기준을 채우는 걸 목표처럼 말했는데, 이번엔 질문(5가지 기준 비교)에 먼저 완전히 답한 뒤 "다섯 기준을 다 갖추는 것 자체가 목표가 아니다"를 마지막에 덧붙였습니다. *(2차 수정: "이 질문에 답하기 전에"로 답을 미루던 구조를 직접 답변 우선 구조로 교정 — `direct-answer-first-correction.md` 참고)*

### Q2. RAG 기반 Q&A 챗봇이 있다면 다섯 기준에서 어디쯤 위치하는가.

**재답변**: "있다면 검색이라는 도구 하나만 쓰는, 챗봇과 에이전트 사이 중간 지대일 겁니다. 다만 강정석님 말씀처럼 '챗봇은 수단이지 목표가 아니'라는 전제를 저도 가져가고 싶습니다. RAG 챗봇이 있다는 사실 자체보다, 그게 어떤 목적(예: 문의 응대 시간 단축)을 실제로 달성했는지가 더 중요한 질문이라고 생각합니다."

**1차 답변과 달라진 점**: 기술적 위치 설명에 그쳤던 이전 답변에, "존재 자체보다 목적 달성 여부가 중요하다"는 강정석 관점을 추가했습니다.

### Q3. 어떤 업무부터 에이전트를 도입해야 하는가, 판단 기준은?

**재답변**: "저는 '어떤 업무부터'보다 먼저 '그 업무의 문제정의가 데이터로 검증됐는가'를 봐야 한다고 생각합니다. 예를 들어 콘텐츠 탐색 마찰 문제라면, 먼저 탐색시간이 길었던 사용자군과 아닌 사용자군의 이후 구독 해지율을 코호트로 비교해서 문제 자체가 맞는지부터 확인합니다. 그게 확인되더라도 바로 에이전트가 아니라, 기존 추천 알고리즘에 행동 신호를 추가하는 것만으로 해결되는지 먼저 봅니다. 이 두 단계를 통과하지 못하는 업무는, 아무리 읽기 전용이라도 에이전트 후보에서 제외하겠습니다."

**1차 답변과 달라진 점**: 이전엔 "읽기 전용 업무부터"라는 일반 원칙에 그쳤는데, 이번엔 "데이터로 검증된 문제인가"를 선행 조건으로 추가했고, "기존 알고리즘으로 먼저 풀어본다"는 단계를 명시적으로 끼워 넣었습니다.

### Q4. 되돌리기 어려운 작업에 에이전트를 적용한다면 어떤 안전장치를 먼저 설계할 것인가.

**재답변**: "가장 먼저 사람이 승인하는 단계를 만들겠습니다. 권한 한도나 로그는 사후 통제지만 승인 단계는 잘못된 실행 자체를 막는 유일한 사전 통제이기 때문입니다. 그다음 발급 수량·금액 한도를 제한하고 모든 실행을 감사 로그로 남기겠습니다. 다만 애초에 되돌리기 어려운 작업까지 에이전트에 맡기는 건, 제가 설계한 5단계 중 가장 마지막 단계에서 그 필요가 검증됐을 때만 검토할 일이라고 생각합니다."

**1차 답변과 달라진 점**: 안전장치 내용 자체는 비슷하되, "이 질문에 답하기 전에 마지막 단계에서만 검토할 일"이라며 답을 미루던 구조를, 안전장치를 먼저 직접 답한 뒤 "마지막 단계에서만"이라는 조건을 끝에 붙이는 구조로 교정했습니다. *(2차 수정: `direct-answer-first-correction.md` 참고)*

### Q5. 챗봇에서 에이전트로 1~3단계를 티빙에 어떻게 적용할 것인가.

**재답변**: "이전에 생각했던 3단계보다 더 보수적으로, 5단계로 다시 설계했습니다. 0단계는 가설 검증 — 탐색 마찰과 해지율의 연결을 코호트로 확인합니다. 1단계는 LLM 없이 기존 추천 알고리즘에 행동 신호만 추가하는 겁니다. 여기서 충분히 좋아지면 사실 여기서 끝입니다. 부족하면 2단계로, 사람이 직접 큐레이션하는 최소 실험으로 기존 알고리즘 대비 효과를 검증합니다. 이게 통과되면 3단계로 검색 도구 하나만 쓰는 RAG 챗봇을 시작하고, 실행까지 필요하다는 근거가 추가로 쌓였을 때만 4단계로 에이전트를 조건부로 확장합니다."

**1차 답변과 달라진 점**: 가장 크게 바뀐 답변입니다. 이전엔 "메타데이터 보강(1단계) → 읽기도구 연결(2단계) → 쓰기도구+검증(3단계)"으로 **에이전트로 가는 걸 전제한** 3단계였는데, 이번엔 "1단계(기존 알고리즘 개선)에서 끝날 수도 있다"는 탈출구를 명시적으로 포함한 5단계로 바뀌었습니다.

## 2. 종합 — 가장 크게 바뀐 것

1차 답변 세트는 "에이전트를 어떻게 잘 설계할 것인가"에 대한 답이었다면, 이번 답변 세트는 **"에이전트를 만들지 않아도 되는 경로를 먼저 확인하고, 그래도 남는 필요에만 조건부로 에이전트를 쓴다"**는 답입니다. 이 차이는 면접관에게 "AI를 쓰고 싶어서 문제를 찾는 사람"이 아니라 "문제부터 보고 필요할 때만 AI를 쓰는 사람"이라는 인상을 주기 위한 것입니다.
