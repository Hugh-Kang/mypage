## 두괄식 답변 (실전용)

> "저는 기술적으로 어려운 이슈가 생기면, 개발자에게 왜 어려운지 원리부터 묻고, 개발 공수를 늘리지 않는 선에서 정책으로 문제를 우회해 일정을 지킨 경험이 있습니다.
>
> 현재 회사는 쿠폰팩 단위로 쿠폰을 발급하는데, 쿠폰팩마다 1인당 1개만 등록할 수 있도록 운영하고 있습니다. 그런데 프로모션 중 한 사용자에게 같은 쿠폰을 2개 이상 발급해야 하는 상황이 생겼는데, '1개 쿠폰 유형을 여러 번 발급하는' 방식으로 정책을 바꾸면 개발 공수가 늘어 출시일 내 테스트가 어려웠고, 쿠폰 번호 체계가 해킹당할 경우 피해가 무한정 커질 위험도 있었습니다.
>
> 그래서 쿠폰 발급 정책 자체는 바꾸지 않고, 해당 월에 쿠폰팩을 2종류 발급해 한 사용자에게 각각 1개씩 지급하는 방식으로 우회했습니다. 이렇게 하니 개발 변경 없이 edge case를 해결하면서, 해킹 시 피해도 쿠폰 1개 단위로 제한할 수 있었습니다.
>
> 이처럼 기술적 제약이 있을 때 왜 어려운지 근본 원인을 먼저 파악하고 정책으로 우회하는 접근이, 티빙에서 복잡한 시나리오를 다룰 때도 도움이 될 거라고 생각합니다."

## 15초 압축판 (말이 길어질 때 대비)

> "쿠폰 중복발급이 필요했던 상황에서, 발급 정책 자체를 바꾸면 개발 공수와 해킹 리스크가 커지는 문제가 있었습니다. 그래서 쿠폰 정책은 그대로 두고 쿠폰팩을 2종류 발급해 1인당 1개씩 지급하는 방식으로 우회해서, 개발 변경 없이 edge case를 해결하고 해킹 피해도 최소화했습니다."

## 구조 요약

| 단계 | 내용 |
|---|---|
| 상황 | 쿠폰팩당 1인 1등록 정책 운영 중, 프로모션으로 한 사용자에게 동일 쿠폰 2개 이상 발급이 필요한 edge case 발생 |
| 문제 | "1유형 다회발급" 방식으로 정책을 바꾸면 ① 개발 공수 증가로 출시일 내 테스트 불가 ② 쿠폰번호 체계 해킹 시 무제한 악용 위험 |
| 해결 | 발급 정책은 유지한 채, 해당 월 쿠폰팩을 2종류로 나눠 발급해 1인당 각 1개씩 지급 — 정책 조합만으로 edge case 우회 |
| 효과 | 개발 변경 없이 일정 준수 + 해킹 피해 범위를 쿠폰 1개 단위로 제한(기존 "무제한 악용" 리스크를 구조적으로 차단) |
| 일반화 | 기술적 제약 상황에서 "왜 어려운지" 원리를 먼저 파악하고, 개발 변경 대신 정책으로 우회하는 접근 — 티빙의 복잡한 시나리오에도 적용 가능 |

## 예상 꼬리질문

| 꼬리질문 | 대응 방향 |
|---|---|
| 왜 발급 매수를 늘리는 대신 쿠폰 종류를 늘리는 방식을 택했나요? | 발급 매수를 유연하게 만드는 쪽은 쿠폰번호 체계 자체를 바꿔야 해 개발 범위가 넓어지지만, 쿠폰 종류를 추가하는 것은 기존 "쿠폰팩 생성" 프로세스를 반복 사용하는 것이라 운영 작업만으로 해결 가능했기 때문이라고 설명 |
| 해킹 피해가 구체적으로 어떻게 제한되나요? | 기존엔 한 쿠폰 유형의 번호 규칙이 뚫리면 동일 쿠폰이 무제한으로 재사용될 위험이 있었지만, 쿠폰을 종류별로 나눠 1인 1개로 제한하면서 설령 번호가 뚫려도 피해가 "쿠폰 1종류 1회분" 규모로 제한된다고 설명 |
| 이 방식이 확장성 측면에서 한계는 없었나요? | 중복발급이 필요한 경우가 1인당 2~3회 수준으로 드물었기 때문에 가능한 임시방편이었고, 만약 중복발급 빈도가 높아진다면 쿠폰번호 체계 자체를 재설계하는 근본적인 개발이 필요하다는 점을 솔직히 인정 |

## 4. 티빙에서 예상되는 유사 사례 2가지

쿠폰 사례의 핵심 구조는 "전체 시스템을 재설계하는 대신, 발급/인증 단위를 조합·주기 조정해 어뷰징 범위만 좁힌다"는 것입니다. 이 구조를 그대로 적용할 수 있는 티빙 도메인 사례 2가지를 제안합니다.

| # | 예상 이슈 | 기술적 제약 | 정책적 우회 방향 |
|---|---|---|---|
| 1 | 통신사·카드사 제휴 무료체험/할인 쿠폰 중복 수령 | 티빙은 SKT 등 통신사·카드사 제휴로 무료체험 쿠폰을 제공하는데, 사용자가 계정을 새로 만들거나 결제수단을 바꿔가며 같은 혜택을 반복 수령할 수 있음. 결제수단·통신 인증 정보를 실시간으로 교차검증하는 시스템을 새로 구축하려면 PG사·통신사 API 연동까지 걸쳐 개발 공수가 매우 큼 | 쿠폰 소진 여부를 "계정" 단위가 아니라 "결제수단(카드번호·통신번호) + 계정" 조합 단위로 체크하도록 발급 정책만 조정 — 기존 발급 시스템 구조는 그대로 두고 중복 수령 판정 기준만 좁힘 |
| 2 | 동시 시청 기기 수(계정 공유) 어뷰징 | 한 계정을 여러 명이 나눠 쓰며 동시 재생 기기 수 제한을 우회하는 문제(넷플릭스의 계정 공유 단속과 유사한 유형). 모든 기기·IP를 실시간으로 추적해 즉시 차단하는 시스템은 트래픽 폭증 시 서버 부담이 크고, 가족 간 정상 사용까지 오탐으로 차단할 위험도 큼 | 실시간 차단 대신 "일정 기간(예: 1개월) 동안 로그인된 기기 수가 N대를 초과하면, 그 다음 로그인부터만 추가 인증(기기 등록 절차)을 요구"하는 방식으로, 실시간 트래킹 부담 없이 비정상 공유 패턴만 주기적으로 걸러냄 |

두 사례 모두 "실시간·완전 자동화된 기술적 해법" 대신 "판정 단위 조합"이나 "체크 주기 조정"이라는 정책 설계만으로 개발 공수를 최소화하면서 어뷰징 범위를 좁힌다는 점에서, 쿠폰 사례와 동일한 해결 패턴을 재사용할 수 있습니다.
