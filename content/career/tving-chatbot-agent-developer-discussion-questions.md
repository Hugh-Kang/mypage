# 티빙 2차 면접 준비 — 챗봇 AI 개발자에게 물어볼 질문 리스트

> 작성 목적: 2차 면접 준비 과정에서 챗봇/AI 에이전트 개발 경험이 있는 개발자와 토의할 기회가 있을 때, 지금까지 설계한 V1(기분 기반 추천)·V2(바이럴 커넥터 에이전트)의 기술적 허점을 보완하기 위해 물어야 할 질문을 정리
> 작성일: 2026-10-14
> 근거자료: `tving-chatbot-mvp-design-socratic-result.md`(V1), `tving-chatbot-mvp-v2-viral-trend-agent-design.md`(V2), `tving-viral-detection-methods-two-examples.md`, `tving-viral-detection-agent-tailquestions.md`

## 핵심 요약 (두괄식)

PM 입장에서 설계한 내용은 "무엇을, 왜"까지는 탄탄하지만, "기술적으로 어떻게 구현되는가"는 검증되지 않은 가정이 많습니다. 개발자와 토의할 시간이 있다면, **① 에이전트의 아키텍처(단순 배치 파이프라인인지, LLM 기반 자율 에이전트인지)**, **② 콘텐츠 매칭의 자동화 가능성과 정확도**, **③ 할루시네이션·오작동 리스크 통제 방법**, **④ 실시간성과 인프라 비용**, **⑤ PM이 설계한 범위가 실제로 공수 추정상 타당한 MVP인지**를 중심으로 질문하는 것이 가장 효율적입니다. 이 답을 미리 들어두면, 면접에서 기술적 디테일을 묻는 꼬리질문에 "실제로 엔지니어와 논의했다"는 근거를 가지고 답할 수 있습니다.

---

## 1. 에이전트 아키텍처 관련 질문

- "제가 설계한 건 '바이럴 신호 수집 → 임계치 판정 → 매칭 → 에디터 승인 → 노출'인데, 이건 정기적으로 도는 배치/파이프라인 형태인가요, 아니면 LLM 기반으로 스스로 판단하는 에이전트 형태로 구현하는 게 더 맞을까요?"
- "'에이전트가 스스로 탐색해서 먼저 행동한다'는 개념을 실제로 구현한다면, 이게 cron 기반 정기 작업인지, 아니면 LLM이 도구(API 호출 등)를 스스로 선택해서 실행하는 agentic workflow인지 — 티빙 같은 서비스에서는 어느 쪽이 더 현실적인가요?"
- "챗봇형 UI(대화창)와, 제가 제안한 '홈 화면에 자동 노출되는 카드' 방식 중 실제 개발 난이도나 유지보수 측면에서 차이가 큰가요?"

## 2. 콘텐츠 매칭/정확도 관련 질문

- "배우명·작품명 기반으로 바이럴 콘텐츠와 티빙 카탈로그를 매칭하려면, 단순 텍스트 매칭보다 임베딩 기반 유사도 매칭이 나을까요? 동명이인이나 맥락 오류를 줄이려면 어떤 방식이 현실적인가요?"
- "진선규가 나온 작품을 자동으로 묶으려면 메타데이터(출연진 정보)가 이미 구조화돼 있어야 할 텐데, 이런 구조화 데이터가 사내에 이미 있다고 가정해도 될까요, 아니면 그것부터 별도 작업이 필요할까요?"
- "'일제강점기 배경'처럼 테마 단위 매칭은 배우 단위 매칭보다 훨씬 구현이 어려울 것 같은데, 기술적으로 이게 가능한 범위인가요, 아니면 MVP에서는 배우/인물 단위로만 한정하는 게 맞을까요?"

## 3. 할루시네이션/오작동 리스크 관련 질문

- "LLM을 이 파이프라인 어딘가에 쓴다면(예: 바이럴 사유 요약, 매칭 근거 설명), 잘못된 정보를 자신 있게 생성하는 할루시네이션 리스크를 어떻게 통제하나요?"
- "에디터 승인 단계를 둬도, 에디터에게 보여줄 '판단 근거'(왜 이게 바이럴로 플래그됐는지) 자체가 잘못 생성되면 승인도 잘못될 수 있는데, 이 근거 생성의 신뢰도는 어떻게 높이나요?"

## 4. 실시간성/인프라/비용 관련 질문

- "검색어 트렌드 API와 소셜 버즈 SaaS API를 매일 혹은 매시간 호출한다고 하면, 실제 인프라 비용이나 운영 부담이 어느 정도 될지 감이 오시나요?"
- "바이럴 감지부터 홈 화면 노출까지, 기술적으로 현실적인 지연 시간(수 분 단위인지 수 시간 단위인지)은 어느 정도로 봐야 할까요?"

## 5. PM 설계 범위의 타당성 관련 질문 (가장 중요)

- "제가 MVP 범위를 '외부 소스 1~2개 채널, 반자동 승인'으로 좁혔는데, 실제 개발 공수 관점에서 이 정도가 2~3개월 내에 현실적인 범위라고 보시나요, 아니면 더 좁혀야 할까요?"
- "혹시 제가 놓친, '이건 PM이 전혀 고려하지 못했을 법한' 기술적 제약이나 리스크가 있을까요?"

## 토의 시 주의할 점

- 질문을 던질 때 "이걸 어떻게 구현해야 하나요"라고 구현 방법 자체를 맡기기보다는, **"제가 이렇게 가정했는데 현실적인가요?"**라는 검증 질문으로 던지는 것이 좋습니다 — 이는 이미 정리해둔 "PM-모델러 권한 경계" 원칙(PM은 정책·범위를 설계하고 전달하되, 구현 방법은 개발자 판단을 존중한다)과도 일관됩니다.
- 토의 내용 중 실제로 반영한 부분이 있다면, 면접에서 "이후 개발자분과 논의하면서 ○○ 부분은 기술적으로 더 좁히는 게 맞다고 다시 설계했습니다"처럼 **협업을 통해 설계를 발전시킨 사례**로 그대로 활용할 수 있습니다.
