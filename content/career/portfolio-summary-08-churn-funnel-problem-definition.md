# 포트폴리오 프로젝트 요약본 ⑧ — 이탈률 퍼널로 문제 정의 (오비랩, AARRR 보드)

## 0. 설계 프롬프트

> 너는 지원자의 포트폴리오 프로젝트 "이탈률 퍼널로 문제 정의"를 면접에서 바로 설명할 수 있는 요약본으로 만드는 코치다. 1분 요약 스크립트는 두괄식으로 — 결론(퍼널에서 무엇을 발견했고 결과가 어땠는지)을 먼저 말한 뒤 배경으로 들어가라. 이 프로젝트는 "왜 화면 구조 자체를 고치지 않고 튜토리얼·툴팁 같은 가벼운 해결책을 택했는가"라는 질문에 자원 제약 상황을 솔직히 인정하며 답하는 게 핵심이다. MAU 증가분(78명, 160%)처럼 상대적 수치가 커 보이지만 절대값은 작다는 점도 숨기지 말고 짚어라.

## 1. 1분 요약 스크립트 (두괄식)

> "저는 AARRR 퍼널 분석으로 사용자의 70%가 마커 설정 구간에서 이탈한다는 걸 발견하고, 그 구간에 튜토리얼 영상과 툴팁을 추가해서 이탈률을 70%에서 26%로 낮췄습니다. 그 결과 MAU가 160%(78명) 늘었고, 분석 서비스 CTR은 1.8배, CVR은 1.5배 올랐습니다. 배경은, 뇌 데이터 분석 서비스 특성에 맞춰 Google Analytics 기반 AARRR 보드를 직접 설계해서 어느 구간에서 사용자가 떠나는지부터 데이터로 확인한 것이었고, 추가 인터뷰로 '마커로 분석 구간을 설정하는 단계가 어렵다'는 원인까지 좁혔습니다. 다만 당시 화면 구조 자체를 바꿀 개발 인력이 부족해서, 근본적인 UI 재설계 대신 튜토리얼과 툴팁이라는 상대적으로 가벼운 해결책을 택했다는 제약이 있었습니다."

## 2. 구조화 (문제정의 → 가설 → 방법론 → 결과 → 회고)

| 단계 | 내용 |
|---|---|
| 문제정의 | GA 기반 AARRR 보드 설계 → 사용자 70%가 마커 설정(버튼 클릭) 구간에서 이탈. 행동데이터+인터뷰로 "마커로 분석구간 설정이 어렵다"는 원인 확인 |
| 가설 | 마커 설정 구간의 어려움이 이탈의 주원인이며, 이 구간에 튜토리얼을 추가하면 이탈률이 줄어들 것이다 |
| 방법론 | 화면 구조 자체를 수정할 개발 인력 부족 → 튜토리얼 영상 제작 + 마커 설정 구간에 툴팁 추가 |
| 결과 | 문제 구간 이탈률 70%→26%, MAU 160%↑(78명), 분석 서비스 CTR 1.8배·CVR 1.5배 |
| 회고(포트폴리오 원문) | 명시적 회고 없음(단, "개발 리소스가 부족한 상황에서의 최선의 선택"이라는 취지의 구두 회고는 존재 — 아래 3절에서 정식화) |

## 3. 회고 (구두 회고를 정식 문서화)

이 프로젝트의 핵심 제약은 개발 리소스였습니다. 마커 설정 구간이 어렵다는 원인까지는 명확히 찾았지만, 화면 구조 자체(버튼 배치, 입력 방식)를 바꾸는 근본적인 해결은 당장 투입할 개발 인력이 없어 불가능했습니다. 그래서 기존 화면은 그대로 두고, 그 위에 튜토리얼 영상과 툴팁을 얹는 방식으로 "지금 가용한 리소스 안에서 가장 빠르게 적용 가능한 해결책"을 택했습니다. 결과적으로 이탈률이 70%에서 26%로 크게 개선된 걸 보면, 문제의 본질이 '화면 자체의 구조적 결함'이라기보다 '설명 부족으로 인한 혼란'에 더 가까웠다는 것도 사후적으로 확인된 셈입니다. 다만 이건 가장 쉬운 해결책이 우연히 잘 맞아떨어진 결과이지, 처음부터 "구조 변경보다 튜토리얼이 더 효과적일 것"이라고 예측하고 선택한 건 아니었다는 한계도 함께 인정합니다.

## 4. 핵심 꼬리질문 1 — "왜 화면 구조 자체를 고치지 않고 튜토리얼·툴팁 같은 가벼운 방법을 택했나요? 근본적인 해결이 아니지 않나요?"

**모범답안(직접답변 우선, 제약 인정)**: "맞습니다, 이건 구조적 재설계가 아니라 우회적인 해결책이었습니다. 당시 화면 구조 자체를 바꾸려면 개발 인력이 투입돼야 했는데, 그 리소스가 당장 없었습니다. 그래서 기존 화면은 그대로 둔 채, 튜토리얼 영상과 툴팁처럼 개발 공수가 훨씬 적게 드는 방법으로 같은 문제(마커 설정의 어려움)에 대응했습니다. 결과적으로 이탈률이 70%에서 26%로 크게 줄어든 걸 보면, 문제의 본질이 '화면 구조 자체의 결함'보다는 '설명이 부족해서 생긴 혼란'에 더 가까웠다는 것도 사후적으로 확인할 수 있었습니다. 다만 이게 처음부터 의도한 최적의 해법이었다기보다, 리소스 제약 안에서 가장 빠르게 시도할 수 있는 것부터 해봤더니 효과가 있었다는 쪽이 더 정확한 설명입니다."

## 5. 핵심 꼬리질문 2 — "MAU 160% 증가라고 하셨는데, 78명이면 절대값은 작은 거 아닌가요?"

**모범답안(직접답변 우선, 축소 없이 인정)**: "맞습니다, 절대 규모로 보면 78명이라는 작은 서비스였습니다. 160%라는 상대적 수치만 강조하면 과장처럼 들릴 수 있다는 것도 알고 있습니다. 다만 이 프로젝트에서 제가 의미 있게 보는 지점은 MAU 절대 규모 자체가 아니라, 이탈률 70%에서 26%로의 변화처럼 '같은 유입 트래픽 안에서 실제로 서비스를 쓰는 사람의 비율'이 크게 개선됐다는 것입니다. 작은 서비스였기 때문에 오히려 퍼널의 특정 구간 하나를 고쳤을 때 전체 숫자에 미치는 영향을 비교적 깨끗하게 관찰할 수 있었던 측면도 있었습니다."

## 6. 그 외 예상 꼬리질문 2가지

### 6-1. "이탈률 개선이 왜 분석 서비스 CTR·CVR 상승으로도 이어졌나요?"

**모범답안**: "퍼널 구조상 자연스러운 결과입니다. 마커 설정 구간에서 70%가 이탈하면, 애초에 분석 결과 화면까지 도달하는 사용자 자체가 적었습니다. 이탈률을 낮춰 더 많은 사용자가 마커 설정을 넘어가게 되면서, 그만큼 더 많은 사용자가 분석 서비스 화면에 도달했고, 그 결과로 분석 서비스에 대한 클릭(CTR)과 전환(CVR)도 함께 늘어난 것으로 해석하고 있습니다. 즉 상류 구간(마커 설정)의 이탈을 줄인 효과가 하류 구간(분석 서비스 이용)까지 자연스럽게 이어진 것입니다."

### 6-2. "70%라는 이탈 지점은 어떻게 정확히 특정했나요?"

**모범답안**: "뇌 데이터 분석 서비스 특성에 맞춰 Google Analytics 기반으로 AARRR 각 단계를 저희 서비스 플로우에 맞게 직접 설계했습니다. 그 보드로 각 단계별 전환율을 보니 마커 설정 버튼 클릭 구간에서 유독 크게 꺾이는 게 데이터로 보였고, 그 수치가 70%였습니다. 이후 왜 그 구간에서 이탈하는지는 행동 데이터만으론 알 수 없어서, 추가 인터뷰로 '마커로 분석 구간을 설정하는 게 어렵다'는 원인까지 확인했습니다."
