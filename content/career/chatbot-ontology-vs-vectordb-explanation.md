# 챗봇 설계 트렌드 — Vector DB vs 온톨로지(지식그래프) 면접용 설명

> 작성 목적: "요즘 챗봇 설계는 vector DB만이 아니라 온톨로지를 주로 쓰는 트렌드"라는 개념을 면접에서 정확하고 자연스럽게 설명할 수 있도록 정리
> 작성일: 2026-09-23
> 성격: 개념 설명 + 본인의 AI 챗봇 프로젝트(마인드로직) 경험과 연결한 답변 스크립트

## 0. 설계 프롬프트

> 너는 AI 프로덕트 개념을 면접에서 설명하기 쉽게 정리해주는 코치다. "챗봇 설계에서 vector DB 중심 RAG에서 온톨로지/지식그래프 중심으로 트렌드가 이동하고 있다"는 주장을 검증하고, ① 두 접근의 핵심 개념과 차이, ② 왜 트렌드가 이동했는지(순수 vector RAG의 한계), ③ 실제로는 "대체"가 아니라 "결합(하이브리드/GraphRAG)"이 표준이 되고 있다는 점을 바로잡고, ④ 지원자 본인의 AI 챗봇 프로젝트 경험과 연결한 1~2분 분량의 면접용 설명 스크립트를 작성하라.

## 1. 먼저 트렌드 자체를 정확히 바로잡기

"vector DB 대신 온톨로지"라는 이분법은 정확한 표현은 아닙니다. 정확히는 **"순수 vector 기반 RAG만으로는 한계가 있어서, 온톨로지/지식그래프를 결합한 하이브리드 구조(대표적으로 GraphRAG)가 트렌드가 되고 있다"**는 것이 맞는 설명입니다. 면접에서 "vector DB 대신 온톨로지를 쓴다"고 말하면 개념을 잘못 안다는 인상을 줄 수 있어, 이 뉘앙스 차이를 정확히 짚고 가는 게 중요합니다.

## 1-1. 온톨로지란 정확히 무엇인가 (기초 정의)

**온톨로지(Ontology)**는 원래 철학 용어(존재론)지만, AI·컴퓨터과학에서는 **특정 도메인의 개념(클래스)과 개체(인스턴스), 그리고 그들 간의 관계·속성·제약조건을 컴퓨터가 이해할 수 있도록 명시적이고 형식적으로 정의한 지식 체계**를 뜻합니다.

핵심 구성요소는 4가지입니다.

| 구성요소 | 의미 | 예시 |
|---|---|---|
| **클래스(Class/Concept)** | 개념의 카테고리 | "아티스트", "그룹", "곡", "팬" |
| **인스턴스(Instance)** | 클래스의 구체적인 사례 | "카리나"는 "아티스트" 클래스의 인스턴스 |
| **관계(Relation)** | 개체 간 연결 | "카리나" —소속— "에스파" |
| **속성(Attribute)** | 개체가 갖는 값 | "카리나".말투 = "발랄함", "카리나".MBTI = "ESTJ" |

여기에 보통 **계층구조(상위-하위 클래스 관계, 예: "아이돌"⊃"보이그룹"⊃"5인조 보이그룹")**와 **제약조건/규칙(예: "모든 곡은 발매한 아티스트가 반드시 있어야 한다")**이 추가되어, 단순히 데이터를 나열하는 걸 넘어 "이 도메인에서 무엇이 참이고 무엇이 가능한지"까지 정의합니다.

**온톨로지 vs 지식그래프(Knowledge Graph)** — 이 둘은 실무에서 자주 혼용되지만 엄밀히는 역할이 다릅니다.
- **온톨로지 = 스키마(설계도)** — "클래스와 관계가 어떻게 정의될 수 있는가"의 틀
- **지식그래프 = 온톨로지(스키마) + 실제 데이터(인스턴스)** — 그 틀 위에 실제 개체와 관계를 채워 넣은 결과물

비유하면, **온톨로지는 회사 조직도의 '양식'**(직급 체계, 부서 간 상하관계를 정의하는 틀)이고, **지식그래프는 그 양식에 실제 직원 이름과 소속을 채운 조직도**입니다.

## 2. 핵심 개념 비교

| | Vector DB (임베딩 기반 RAG) | 온톨로지 / 지식그래프 |
|---|---|---|
| **저장 방식** | 텍스트를 임베딩 벡터로 변환해 저장 | 개체(entity)와 관계(relation)를 노드-엣지 구조로 명시적으로 정의 |
| **검색 방식** | 질의를 벡터화해 코사인 유사도 등으로 "의미적으로 유사한" 텍스트 조각을 검색 | 그래프를 따라가며 "누가-무엇을-어떻게" 관계를 조회 |
| **강점** | 비정형 텍스트, 자유로운 표현·유사 문장 매칭에 강함. 구축이 상대적으로 쉬움 | 관계 기반 다단계 추론(multi-hop reasoning), 사실 일관성 보장, 결과를 "왜 그런지" 설명 가능(explainability) |
| **약점** | 관계·인과관계·다단계 추론에 약함. 같은 질문에 매번 다른 근거 문서가 걸려 답이 미묘하게 달라질 수 있음(일관성 저하) | 구축·유지보수 비용이 큼. 모든 자연어 지식을 그래프로 구조화하는 건 비현실적 |
| **대표 실패 사례** | "이 캐릭터의 친구의 친구는 누구야?" 같은 관계 질문에 유사도 검색만으로는 정확히 답하기 어려움 | 자유로운 잡담이나 비정형 리뷰 텍스트 전체를 다 그래프로 만들기는 어려움 |

## 3. 왜 트렌드가 "결합"으로 이동했는가

순수 vector RAG만 쓰는 챗봇에서 흔히 나오는 문제는 이렇습니다.

- **관계 질문에 약함**: "A가 B의 상사인가?" 같은 질문은 벡터 유사도로는 정확히 풀리지 않음 — 이런 질문은 그래프를 따라가는 게 훨씬 정확함
- **사실 일관성이 깨짐**: 챗봇이 어제는 "A"라고 답했는데 오늘은 조금 다른 문서 조각이 검색돼 "A'"라고 답하는 문제 — 지식그래프는 관계를 한 번 정의하면 항상 동일하게 조회되므로 이 문제를 줄여줌
- **설명 가능성 부족**: 벡터 검색은 "왜 이 문서가 뽑혔는지"를 사람이 이해하기 어려운 반면, 그래프는 경로(A→관계→B)를 그대로 보여줄 수 있어 디버깅·신뢰성 확보에 유리

그래서 마이크로소프트의 **GraphRAG**를 계기로, "비정형 텍스트는 vector DB로, 명확한 관계·사실은 지식그래프로" 나눠서 담당시키고, 질의가 들어오면 두 소스를 함께 조회해 결합하는 **하이브리드 RAG**가 실무 표준으로 자리잡고 있습니다.

## 4. 본인 경험과 연결 — 마인드로직 AI 챗봇 프로젝트

이 개념을 설명할 때 가장 설득력 있는 방법은, 본인이 이미 비슷한 문제를 실무에서 겪었다는 걸 보여주는 것입니다.

- 마인드로직 AI 아이돌 챗봇 프로젝트에서, 아티스트의 **페르소나를 설정하는 20가지 요소**(말투, 이모지 사용, MBTI 등)와 **아티스트 전용 Memory 관리**(공개하고 싶지 않은 정보를 직접 수정·삭제) 기능을 설계한 적이 있음
- 이건 사실 "아티스트(entity) — 속성/관계(attribute·relation) — 값"을 구조화해서, 챗봇이 **같은 질문에는 항상 같은 답**을 하도록 일관성을 보장하려 한 설계였음 — 당시엔 "온톨로지"라는 용어를 쓰지 않았지만, 목적 자체는 온톨로지가 풀려는 문제(관계 일관성)와 동일했음
- 반면 팬과의 자유로운 잡담 대화 자체는 채팅 로그를 분석해 관심 주제를 추출하고 그에 맞는 텍스트를 생성하는, 비정형 텍스트 기반 접근(=vector/임베딩 계열 접근에 가까움)이었음
- 즉, 본인도 모르게 "구조화된 사실(온톨로지적 접근)"과 "비정형 대화(벡터 기반 접근)"를 역할별로 나눠서 설계했던 경험이 있는 셈

## 5. 면접용 설명 스크립트 (1~2분)

> "요즘 챗봇 설계 트렌드를 말씀드리면, 'vector DB 대신 온톨로지'라기보다는 **'vector DB 기반 RAG의 한계를 온톨로지, 즉 지식그래프로 보완하는 하이브리드 구조'가 표준이 되고 있다**고 보는 게 더 정확합니다.
>
> 벡터 DB는 텍스트를 임베딩으로 바꿔서 의미적으로 유사한 문서를 찾아오는 방식이라 비정형 텍스트 검색에는 강하지만, '이 사람과 저 사람이 어떤 관계인지' 같은 관계 기반 질문이나 다단계 추론에는 약하고, 같은 질문에도 매번 다른 문서 조각이 걸려서 답이 미묘하게 달라지는 일관성 문제가 있습니다. 그래서 명확한 관계나 사실은 노드-엣지 구조의 지식그래프로 따로 관리하고, 자유로운 대화 맥락은 벡터 검색으로 처리하는 GraphRAG 같은 하이브리드 방식이 최근 트렌드입니다.
>
> 저도 비슷한 문제를 실제로 겪은 적이 있는데요, AI 아이돌 챗봇 프로젝트에서 아티스트의 페르소나와 설정 정보는 구조화된 속성·관계로 관리해서 항상 같은 질문에 같은 답을 하도록 일관성을 보장했고, 팬과의 자유로운 잡담은 채팅 로그 기반의 비정형 텍스트 생성으로 처리했습니다. 그때는 '온톨로지'라는 용어를 쓰지 않았지만, 지금 생각해보면 구조화가 필요한 사실과 자유로운 대화를 역할별로 나눠서 설계했던 것 자체가 같은 문제의식이었다고 생각합니다."

## 6. 예상 후속 질문 대비

- **"그럼 어떤 경우에 온톨로지를, 어떤 경우에 벡터DB를 쓰면 될까요?"** → 일관성이 깨지면 안 되는 사실(가격, 관계, 정책, 캐릭터 설정)은 그래프로, 자유로운 텍스트·후기·잡담처럼 비정형이고 유사도 기반 검색이 필요한 영역은 벡터DB로 나누는 게 기준이라고 답하면 됨
- **"GraphRAG를 실제로 써본 적은 있나요?"** → 직접 GraphRAG라는 이름의 프레임워크를 쓴 적은 없다면, 솔직히 그렇게 답하되 "다만 구조화된 정보와 비정형 정보를 나눠 설계한 경험은 있다"고 위 4번 내용으로 연결할 것
