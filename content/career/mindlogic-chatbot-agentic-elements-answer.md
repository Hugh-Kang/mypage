# 아이돌 챗봇에서 "AI 에이전트"적인 부분은 무엇이었나 — 시나리오 2가지

> 작성 목적: "LLM이 목표를 분해하고 도구를 스스로 선택해 호출하며 결과를 검증하는 루프를 도는 것"이 에이전트라는 정의를 전제로, 마인드로직 아이돌 챗봇 프로젝트 중 이 정의에 해당할 수 있는 요소를 구체적 시나리오 2가지로 제안
> 작성일: 2026-10-01
> 근거자료: `mindlogic-chatbot-hallucination-management-answer.md`(사실정보 vs 자유대화 분리 설계), `mock-interview-parkjinhyeong-structured.md`(아티스트 스케줄 정보 실시간 반영 언급), `tving-discovery-role-priority.md`(이 챗봇이 "페르소나 대화"에 가깝고 "작업 수행형 에이전트"와는 다를 수 있다는 기존 리스크 인식)

## 0. 설계 프롬프트

> 너는 "목표 분해 → 도구를 스스로 선택·호출 → 결과 검증"이라는 에이전트 정의를 전제로, 지원자의 실제 프로젝트(마인드로직 아이돌 챗봇)에서 이 정의에 부합할 수 있는 요소를 찾아야 한다. 없는 기능을 지어내지 말고, 이미 확인된 사실(아티스트 설정 정보의 구조화 관리, 스케줄 정보 실시간 반영, 사실정보/자유대화 분리)에서 출발해 2개의 구체적 시나리오를 제안하라. 다만 실제로 "LLM이 스스로 판단해서 도구를 호출했는지"(에이전트적) 아니면 "사전에 고정된 분기 로직이 처리했는지"(단순 파이프라인)는 확인되지 않았으므로, 이 경계를 답변에 명확히 포함하라.

## 1. 먼저 짚을 것 — 에이전트 vs 파이프라인의 경계

제안하는 두 시나리오 모두, **실제로 LLM이 "지금 도구를 호출해야 하는지"까지 스스로 판단했다면 에이전트적 요소**이고, 반대로 **사전에 정해진 분류기(if-else 또는 고정 라우팅)가 처리한 것이라면 에이전트라기보다는 일반적인 파이프라인**에 가깝습니다. 이 경계가 정확히 어느 쪽이었는지는 당시 설계를 다시 확인해야 하는 부분이라, 면접에서는 "이렇게 설계했다면 에이전트적 요소로 볼 수 있다"는 조건부 화법으로 답하는 것이 정직합니다.

## 2. 시나리오 1 — 실시간 스케줄 조회를 통한 답변 (Tool-calling)

**시나리오**: 팬이 챗봇에게 "오늘 뭐해?", "이번 주 스케줄 있어?"라고 물으면, 챗봇이 이 질문을 "지금 이 순간의 최신 정보가 필요한 질문"으로 인식하고, 그냥 지어내서 답하는 대신 먼저 아티스트 스케줄 데이터를 조회한 뒤 그 결과를 반영해 답하는 흐름입니다.

| 요소 | 내용 |
|---|---|
| 목표 분해 | "오늘 뭐해?"라는 질문을 "대화 생성"이 아니라 "먼저 최신 스케줄 데이터 확인이 필요한 질문"으로 하위 목표를 나눔 |
| 도구 호출 | 아티스트 스케줄 DB/API를 조회하는 함수를 호출 |
| 결과 검증 | 조회 결과가 비어 있거나 당일 데이터가 없으면, 추측성 답변 대신 "지금은 스케줄 정보가 없다"는 안전한 대체 응답으로 전환 |

**기술 예시**: LLM API의 function calling(tool use) 스펙을 활용해 `get_artist_schedule(date)` 같은 함수 시그니처를 정의하고, 사용자 발화를 분석해 이 함수 호출이 필요한지를 LLM이 스스로 판단하도록 설계하는 방식입니다.

## 3. 시나리오 2 — 자유 대화 중 사실 확인이 필요한 발화를 스스로 감지해 구조화 데이터를 조회

**시나리오**: 자유로운 잡담 흐름 중에 "생일이 언제야?" 같은 사실 질문이 갑자기 섞여 들어오면, 챗봇이 그 순간만 "이 부분은 추측이 아니라 사실을 조회해야 한다"는 하위 목표로 분리해서 처리하는 흐름입니다.

| 요소 | 내용 |
|---|---|
| 목표 분해 | 전체 대화 흐름(자유 생성)과 별개로, 사실 확인이 필요한 특정 발화만 분리해서 처리할 하위 목표로 설정 |
| 도구 호출 | 아티스트 설정 정보(구조화된 관계 데이터)를 조회하는 쿼리를 실행 |
| 결과 검증 | 생성하려는 답변이 조회된 사실과 일치하는지 다시 비교해서, 불일치하면 재생성하거나 사실 데이터를 우선 반영 |

**기술 예시**: RAG(검색 증강 생성) 구조에서 한 단계 더 나아가, "이 질문에 검색이 필요한지 여부"까지 LLM이 스스로 판단하게 하는 방식(예: Self-RAG 개념)입니다. 모든 질문에 무조건 검색을 강제하는 게 아니라, LLM이 "이건 사실 확인이 필요하다"고 자체적으로 판단해서 검색 여부와 시점을 결정하는 구조입니다.

## 4. 면접용 답변

> "두 가지를 제안드릴 수 있을 것 같습니다. 첫째는 아티스트 스케줄 정보를 반영하는 부분인데, 팬이 '오늘 뭐해?'라고 물으면 챗봇이 그 자리에서 지어내지 않고 먼저 스케줄 데이터를 조회한 뒤 그 결과로 답하는 흐름입니다. 이게 LLM의 function calling으로, 질문을 보고 LLM이 스스로 '지금 스케줄 조회가 필요하다'고 판단해서 도구를 호출하도록 설계됐다면 에이전트적 요소라고 볼 수 있습니다. 둘째는 자유로운 잡담 중에도 생일 같은 사실 질문이 섞여 들어오면, 그 부분만 구조화된 설정 데이터를 조회해서 사실과 일치하는지 확인하고 답하는 흐름입니다. 다만 이 두 가지가 실제로 LLM이 그때그때 스스로 '도구를 호출할지 말지'까지 판단한 것이었는지, 아니면 사전에 정해진 분류 로직이 처리한 것이었는지는 지금 다시 확인이 필요한 부분이고, 전자라면 명확히 에이전트적 요소, 후자라면 일반적인 파이프라인에 더 가깝다고 정직하게 말씀드리고 싶습니다."
