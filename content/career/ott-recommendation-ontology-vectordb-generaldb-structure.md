# OTT 콘텐츠 추천 — 온톨로지 vs 벡터DB vs 일반 DB, 어디에 무엇을 쓰는가

> 작성 목적: 티빙·넷플릭스·쿠팡플레이 같은 OTT의 콘텐츠 추천 파이프라인을 단계별로 나눠, 온톨로지·벡터DB·일반(관계형/NoSQL) DB가 각각 어느 항목에 쓰이는지 구조화하고 직관적으로 설명
> 작성일: 2026-09-29
> 근거자료: `chatbot-ontology-vs-vectordb-explanation.md`(온톨로지·벡터DB 기초 개념), `tving-recommendation-data-structure-answer.md`(OTT 추천 데이터 유형 구조화). 특정 OTT사의 실제 내부 아키텍처는 공개된 바 없으므로, 이 문서의 회사별 예시는 **일반적인 추천 시스템 설계 원리에 기반한 추정**임을 전제로 함

## 0. 설계 프롬프트

> 너는 OTT 추천 시스템 아키텍처를 면접에서 설명해야 하는 지원자를 돕는 코치다. 콘텐츠 추천이 일어나기까지의 전체 파이프라인을 몇 개의 단계로 나누고, 각 단계에서 왜 온톨로지가 아니라 벡터DB가, 혹은 일반 DB가 쓰이는지 그 이유(데이터의 성격, 필요한 질의 방식)를 근거로 구조화하라. 티빙·넷플릭스·쿠팡플레이를 예시로 들되, 실제 내부 구조를 안다고 단정하지 말고 "일반적인 추천 시스템 설계 원리로 미루어보면"이라는 전제를 명시하라. 마지막으로 비전문가도 바로 이해할 수 있는 비유로 세 가지 DB의 역할 차이를 요약하라.

## 1. 핵심 원리 — "데이터의 성격"이 DB 선택을 결정한다

세 가지 DB는 경쟁 관계가 아니라, **애초에 다른 종류의 질문에 답하도록 만들어진 도구**입니다.

| DB 종류 | 잘 답하는 질문의 형태 | 데이터의 성격 |
|---|---|---|
| **일반 DB (관계형/NoSQL)** | "이 사용자가 결제한 구독 등급은?", "이 사용자가 어제 몇 시에 몇 분 시청했는가?" | 정확한 값 하나를 빠르고 정확하게 찾아야 하는 **거래·이력 데이터** |
| **온톨로지 / 지식그래프** | "이 배우가 출연한 다른 시리즈물은?", "이 장르와 저 장르는 어떤 관계인가?" | 항목 간 **명확한 관계와 규칙**으로 정의되는 **구조화된 지식** |
| **벡터DB** | "이 영화와 '분위기'가 비슷한 콘텐츠는?", "줄거리가 이거랑 느낌이 비슷한 작품은?" | 명시적 규칙으로 정의하기 어려운 **의미적 유사성** |

## 2. 추천 파이프라인 단계별 구조화

| 단계 | 무엇을 해야 하는가 | 쓰이는 DB | 왜 그 DB인가 |
|---|---|---|---|
| ① 사용자 식별·자격 확인 | 로그인, 구독 등급, 결제 상태, 프로필(가족 내 개인 프로필) 확인 | **일반 DB** | 정확히 일치하는 값(구독 등급이 프리미엄인지 등)을 빠르게 조회해야 하는 전형적인 트랜잭션 데이터 |
| ② 행동 로그 적재 | 시청 시작·완료율·이탈 지점·검색어·클릭 로그 수집 | **일반 DB (대용량 로그 스토어)** | 시간 순서가 있는 대량의 이벤트 기록 — 정형화된 스키마(user_id, event_time, event_type)로 관리 |
| ③ 콘텐츠 속성·관계 정의 | 장르, 출연진, 감독, 시즌/회차, "이 배우가 나온 다른 작품", "이 시리즈의 세계관 연결 작품" 같은 명시적 관계 | **온톨로지 / 지식그래프** | "장르가 스릴러이면서 이 배우가 나온 작품"처럼 **명확한 규칙 기반 질의**에 강함. 관계 자체가 데이터이므로 그래프 구조가 자연스러움 |
| ④ 줄거리·리뷰·자막 등 비정형 텍스트의 의미 검색 | "느낌이 비슷한 영화", "이런 분위기의 작품" 같은 모호한 유사도 기반 탐색 | **벡터DB** | 장르 태그로는 못 잡는 **의미적 유사성**(둘 다 '잔잔한 성장 드라마'라는 톤)을 임베딩 거리로 계산 |
| ⑤ 협업 필터링(유사 취향 사용자 기반 추천) | "이 콘텐츠를 본 사람들이 함께 본 콘텐츠" | **벡터DB 또는 전용 추천 엔진** | 사용자·콘텐츠를 임베딩 공간에 투영해 유사도 계산 — 벡터 연산에 최적화된 저장소가 유리 |
| ⑥ 실시간 랭킹·서빙 | 최종적으로 "지금 이 사용자에게 어떤 순서로 몇 개 보여줄지" 결정 | **일반 DB(캐시/인메모리) + 위 결과들을 조합** | 응답 속도가 핵심이라, 앞 단계 결과를 미리 계산해두고 빠르게 조회만 하는 구조가 필요 |

## 3. 회사별 예시로 구체화 (일반적인 추천 시스템 설계 원리로 미루어본 추정)

> 주의: 아래는 각 회사의 공개된 내부 아키텍처가 아니라, 각 회사의 서비스 특성상 어떤 데이터가 특히 중요할지 **일반 원리로 추론한 것**입니다.

| 회사 | 온톨로지가 특히 중요할 지점 | 벡터DB가 특히 중요할 지점 | 일반 DB가 특히 중요할 지점 |
|---|---|---|---|
| **티빙** | KBO 중계처럼 "이 팀·이 선수·이 경기"라는 명확한 관계가 있는 스포츠 콘텐츠, 시리즈물의 세계관·시즌 연결 관계 | 예능·드라마의 "분위기/케미"가 비슷한 작품 추천(장르 태그만으론 부족한 부분) | 실시간 시청 이벤트, 구독 등급, 프로필별 시청 이력 |
| **넷플릭스** | 대규모 글로벌 카탈로그의 언어·국가·등급 분류 체계 | 전 세계 취향이 제각각인 사용자에게 "톤이 비슷한" 작품을 국가·언어 경계 없이 추천 | 초대규모 사용자 행동 로그(초 단위 시청 위치 등) |
| **쿠팡플레이** | 스포츠 중계(해외축구 등) 일정·리그·팀 관계, 커머스 연계(쿠팡 상품과 콘텐츠 태그 연결) | 커머스 구매 이력과 연계된 "이런 상품 좋아하는 사람이 좋아할 콘텐츠" 같은 교차 도메인 유사도 | 로켓배송 회원 등급과 연동된 구독·결제 데이터 |

## 4. 비전문가도 바로 이해할 수 있는 비유

> **일반 DB**는 "장부"입니다. 누가 언제 무엇을 봤는지, 얼마를 냈는지를 정확하게 기록하고 빠르게 찾아보는 역할입니다.
>
> **온톨로지**는 "백과사전의 색인/족보"입니다. "이 배우는 이 작품에도 나왔다", "이 장르는 저 장르의 하위 개념이다"처럼 항목들 사이의 **명확한 관계**를 표로 정리해둔 것입니다.
>
> **벡터DB**는 "취향이 통하는 친구의 감"입니다. 명확한 규칙으로는 설명 못 해도 "이거 좋아하면 저것도 좋아할 것 같다"는 **애매하지만 강력한 직감**을 숫자(임베딩)로 흉내 낸 것입니다.

## 5. 셋을 함께 쓰는 이유 (하이브리드가 기본)

실제로는 세 가지 중 하나만 쓰는 경우는 드뭅니다. 예를 들어 "이 사용자에게 무엇을 추천할까"라는 하나의 요청 안에서도, **일반 DB로 이 사용자의 구독 등급과 최근 시청 이력을 확인하고 → 온톨로지로 명확한 관계(같은 시리즈의 다음 시즌, 같은 감독의 다른 작품)를 먼저 후보에 넣고 → 벡터DB로 "느낌이 비슷한" 후보를 추가로 채운 뒤 → 그 후보들을 일반 DB/캐시에서 빠르게 정렬해서 서빙**하는, 하나의 파이프라인 안에서 세 가지가 순차적으로 협업하는 구조가 일반적입니다.

## 6. 면접용 요약 답변

> "OTT 추천은 하나의 DB로 되는 게 아니라 역할이 다른 세 가지가 함께 씁니다. 사용자의 구독 등급이나 시청 로그처럼 정확한 값을 빠르게 조회해야 하는 부분은 일반 DB가 맡고, '이 배우가 나온 다른 작품'처럼 명확한 관계로 정의되는 부분은 온톨로지·지식그래프가 맡습니다. 그리고 '분위기가 비슷한 콘텐츠'처럼 규칙으로 딱 잘라 말하기 어려운 의미적 유사성은 벡터DB가 맡습니다. 실제 추천은 이 셋을 파이프라인 안에서 순서대로 조합해서, 먼저 명확한 관계로 후보를 좁히고 그다음 유사도로 후보를 넓히는 방식으로 이뤄진다고 생각합니다."
