## 0. 설계 프롬프트

> 너는 지원자의 마인드로직 AI 챗봇(블루밍) 프로젝트에 대해, "어떤 기능 구간에서 LLM API를 썼는가", "RAG 챗봇은 어디에 활용됐는가"를 추론하는 기술 분석가다. 이 세션에서 이미 확인된 사실(페르소나 정보는 구조화된 속성으로 관리, 자유 잡담은 채팅로그+프롬프트 기반 생성형, QA 골든셋으로 사전 검증, 다국어 번역에 OpenAI API 사용, 관심주제 데이터 수집에 AI 자동생성 경로 포함)만을 근거로 각 기능 구간이 LLM API를 썼을 가능성과, RAG(검색 후 생성) 패턴에 해당하는지를 추론하라. 확인된 사실과 유추를 절대 섞지 말고 표로 명확히 구분하고, 김현우가 언급한 "벡터화 기반 대화형 추천" 아이디어는 블루밍의 실제 구현이 아니라 티빙을 위한 제안이었다는 점을 혼동하지 마라.

## 1. 전제 — 확정 사실과 유추의 경계

| 구분 | 내용 |
|---|---|
| **확정 사실** | 페르소나·설정 정보(생일·데뷔·멤버관계·세계관)는 구조화된 속성·관계로 관리됨 |
| **확정 사실** | 자유 잡담은 채팅 로그+프롬프트가 결합된 인풋으로부터 생성되는 비정형 텍스트(생성형) |
| **확정 사실** | 배포 전 QA팀과 골든셋(의도된 정답 세트)으로 사전 검증 |
| **확정 사실** | 관심주제 데이터는 아티스트 전용 챗봇·매니저 콘솔·AI 자동생성 3개 경로로 수집 |
| **확정 사실(다른 프로젝트)** | 언어 패키지 프로젝트에서 OpenAI API로 한→중/일 등 다국어 자동 번역 수행 |
| **유추 금지 영역** | 실제 벡터DB 제품 도입 여부, 정식 온톨로지 스키마/그래프DB 사용 여부 — 개발자 본인이 "기억 안 난다"고 명시적으로 밝힌 부분 |
| **혼동 주의** | 김현우가 말한 "콘텐츠 요소별 벡터화 + 하이브리드 유사도" 아이디어는 **티빙 챗봇을 위한 제안**이었지, 블루밍이 실제로 그렇게 구현됐다는 확인은 아님 |

## 2. 기능 구간별 LLM API 사용 여부 유추

| 기능 구간 | LLM API 사용 추론 | 근거/추론 신뢰도 |
|---|---|---|
| 자유 잡담 응답 생성 | **사용(추론, 신뢰도 높음)** | "채팅로그+프롬프트 인풋 → 비정형 텍스트 생성"이라는 확정 사실 자체가 LLM의 전형적 동작 방식. 실시간 대화 생성이므로 GPT 계열 등 상용 LLM API를 실시간 호출했을 가능성이 가장 큼 |
| 사실 기반 질문 응답(생일·멤버관계 등) | **사용(추론, 신뢰도 높음)** | 구조화 데이터를 "조회"만으로 끝내지 않고 자연스러운 문장으로 답했을 것이므로, 조회된 사실을 LLM에 근거로 넣어 자연어로 포장하는 단계에서 LLM API가 쓰였을 것으로 추론 |
| 관심주제 데이터 수집 — AI 자동생성 경로 | **사용(추론, 신뢰도 중간)** | 3개 경로 중 하나가 명시적으로 "AI 자동생성"이라 불리므로, 특정 관심주제에 대한 응답 예시·대화 스크립트를 오프라인에서 LLM으로 대량 생성해 챗봇 데이터로 축적했을 가능성 |
| 다국어 번역 | **사용(확정)** | 포트폴리오 프로젝트 ⑥에 "OpenAI API로 자동 번역"이라고 명시 |
| QA 골든셋 테스트케이스 생성 | **사용 여부 불명확(순수 유추)** | 사람이 직접 만들었을 수도, LLM 보조로 초안을 만들고 사람이 검수했을 수도 있음 — 확인된 바 없음 |
| 매니저 콘솔 경로(관심주제 데이터 수집) | **미사용 추론** | '콘솔'이라는 표현상 사람(매니저)이 직접 입력하는 인터페이스일 가능성이 높아, 이 경로 자체는 LLM 호출 없이 사람이 직접 데이터를 넣는 구간으로 추론 |

## 3. RAG(검색 증강 생성) 패턴이 적용됐을 것으로 보이는 구간

**결론부터**: RAG 패턴에 가장 가깝게 작동했을 구간은 **사실 기반 질문 응답(페르소나·설정 정보)** 입니다.

**추론 근거**: RAG는 본질적으로 "① 관련 정보를 먼저 조회(retrieve) → ② 그 정보를 LLM 프롬프트에 근거로 주입(augment) → ③ 자연어로 답변 생성(generate)"하는 흐름입니다. 확정된 사실인 "아티스트 설정 정보를 구조화된 속성으로 관리하고, 사실 기반 질문에 그 정보를 참조 데이터로 제공했다"는 서술이 정확히 이 흐름과 일치합니다. 사용자가 "OO 생일이 언제야?"라고 물으면, 구조화된 데이터에서 생일 값을 조회(retrieve)한 뒤 그 값을 LLM에 근거로 넣어 "OO 생일은 X월 X일이에요!" 같은 자연스러운 문장으로 포장(generate)했을 것으로 추론됩니다.

**다만 분명히 구분해야 할 점**: 이게 "벡터DB 기반 RAG"였는지는 확정할 수 없습니다. RAG는 검색 방식이 꼭 벡터 유사도 검색일 필요는 없고, 구조화된 DB에서 정확히 일치하는 값을 조회(exact lookup)하는 것도 넓은 의미의 "검색 후 생성" 구조에 해당합니다. 확인된 사실 수준에서는 "구조화된 속성 조회"라고만 되어 있어서, 벡터 유사도 검색 기반이었다고 말하면 과장이 됩니다. 반대로 자유 잡담 구간은 "조회 후 생성"이 아니라 "채팅로그+프롬프트를 바로 생성에 사용"하는 구조라, RAG라기보다는 순수 생성형(혹은 In-context 대화 이력 기반 생성)에 가깝습니다.

## 4. 면접에서 이 추론을 말할 때 주의할 점

면접관이 "그래서 그 사실 기반 답변 구간이 RAG였나요?"라고 구체적으로 캐물으면, 다음과 같이 추론과 확정을 구분해서 답하는 것을 권장합니다.

> "확정적으로 'RAG였다'고 말씀드리긴 조심스럽습니다. 다만 사실 기반 질문에는 구조화된 정보를 먼저 조회한 뒤 그 내용을 LLM에 근거로 제공해 자연어로 답했다는 건 확실한 설계였고, 이건 '검색 후 생성'이라는 RAG의 기본 구조와 같은 방향입니다. 다만 그 검색이 벡터 유사도 기반이었는지, 단순 구조화 DB 조회였는지까지는 프로젝트가 오래돼 정확히 확인하기는 어렵습니다."

## 5. 종합

| 구간 | LLM API | RAG 해당 여부 |
|---|---|---|
| 자유 잡담 생성 | 사용(추론) | 아니오 — 순수 생성형(대화이력 기반) |
| 사실 기반 질문 응답 | 사용(추론) | **예에 가까움** — 구조화 데이터 조회 후 생성 |
| 관심주제 AI 자동생성 데이터 | 사용(추론, 오프라인) | 아니오 — 생성 전용 |
| 다국어 번역 | 사용(확정) | 아니오 — 번역 completion 작업 |
| 매니저 콘솔 입력 | 미사용(추론) | 해당 없음 |
