# 현대자동차 AVP 차량 프로젝트관리(상품성평가) — 자기소개서 소재 구조화 및 우선순위

> 지원 공고: AVP 차량 프로젝트 관리 — 차량 총합 상품성 평가(UX/HMI) 트랙
> 작성일: 2026-09-05
> 성격: 자소서 문항별 소재 배분 전략 — 신입 공채는 포트폴리오 제출 구간이 없어, 자소서가 유일한 실적 증거 제출 창구임을 전제로 설계

## 0. 설계 프롬프트

> 당신은 현대자동차 신입 공채 자기소개서 첨삭 전문가입니다. 아래 두 개의 자기소개서 문항과 지원자의 이력서·포트폴리오에 담긴 프로젝트 사례 전체를 검토해, ① 각 문항이 실제로 평가하려는 축(동기/비전 vs 경험/성장)을 분리하고, ② 지원자의 전체 프로젝트 후보를 인벤토리화한 뒤 문항별 적합도를 채용공고 우대사항·직무 키워드에 근거해 판정하고, ③ 문항별로 우선순위 순서를 매기고 왜 그 순서인지 설명하고, ④ 신입 공채에는 포트폴리오 제출 구간이 없다는 제약을 감안해 자소서 안에서 반드시 압축해 넣어야 할 요소(수치, 문제-원인-해결 구조)를 1,000자 분량 제약과 함께 제시하세요. 추측이 아니라 공고 원문과 이력서·포트폴리오에 실제 등장하는 표현·수치를 근거로 삼으세요.

## 1. 문항 성격 분석 — 무엇을 증명해야 하는가

| 문항 | 요구 형식 | 평가자가 실제로 보는 것 | 포트폴리오 부재의 함의 |
|---|---|---|---|
| 자소서1: 지원동기 + 입사 후 그리고 싶은 내일 (1,000자) | 동기·비전 서술 | "왜 우리 회사·이 팀인가", "얼마나 구체적인 미래상을 갖고 있는가" — 오래 남아 기여할 사람인지 | 경험은 근거로만 짧게 인용, 메인은 방향성 |
| 자소서2: 차별화된 가능성 경험 + 성장 과정 (1,000자) | 단일 경험 서사 | "실제로 무엇을 했고, 어떤 임팩트를 냈고, 무엇을 배웠는가" | **포트폴리오를 대체하는 유일한 창구.** 문제-역할-과정-결과-회고를 1,000자 안에 압축해야 함 |

**핵심 원칙**: 두 문항에 같은 프로젝트를 깊게 두 번 쓰면 정보량이 줄어든다. 자소서1은 방향성 중심으로 경험을 "인용"만 하고, 자소서2가 그 경험을 깊게 푸는 방식으로 **소재를 분리**해야 한다.

## 2. 전체 소재 인벤토리 (이력서·포트폴리오 기준)

| 프로젝트 | 핵심 내용 | JD 우대사항과의 접점 | 정량 성과 |
|---|---|---|---|
| ① 마인드로직 — AI챗봇과의 상호작용 개선 | 대화 불만족 83% 원인 분석 → 사용자 시나리오 설계 → AB test → 지표 개선 | 사용자 시나리오 설계, UX 평가·검증, 평가결과 기반 개선안 도출 — **JD 워크플로우와 거의 1:1** | 만족도 30%↑, linguistic/interaction cue 25%↑, 중국 MAU 5,000명 |
| ② 석사 논문 — 스마트스피커 음성 상호작용 반응시간·청각피드백 연구 | HMI 실험 설계·분석 | "인간공학 전공" 우대사항의 학술적 근거 | 정량 성과 없음(학위논문) |
| ③ 오비이랩 — 측정 소프트웨어 사용성 개선 | 사용자/이해관계자 인터뷰 → 인사이트 도출 → 단계별 구조·피드백 설계 | 사용성 평가, 사용자 리서치 — 교과서적 사용성평가 방법론 | 측정 준비시간 70%↓(평균 40초) |
| ④ 오비이랩 — 노인 사용자를 고려한 과제 추가 | 취약 사용자군 행동데이터 분석 → 난이도 조정 과제 설계 | 다양한 사용자 특성을 배려한 UX 설계 | 서비스 사용자 107%↑ |
| ⑤ 오비이랩 — 이탈률 퍼널로 문제 정의 | GA 기반 이탈 퍼널 분석 → 튜토리얼 삽입 | 사용자 행동 데이터 기반 UX 개선 | 이탈률 70%→26%, MAU 160%↑ |
| ⑥ 볼트업 — 홈화면 충전구역 추천 고도화 | 행동데이터 세그먼트 분석 → 추천 로직 재설계 | 데이터 기반 UX 개선(현재 재직 중 최신 사례) | CTR 7%↑, VOC 47%↓ |
| ⑦ 볼트업 — 카카오T 결제 정합성 설계 / U+ 쿠폰 인증 절차 | 파트너사 리스크 협의, 인증 정책 설계 | 상품성평가·UX/HMI와 직접 연관 낮음(정책·리스크 관리형) | CS 건수 월 0건 유지 / 매출 16%↑ |
| ⑧ 빵그리의오븐 — 상품 추천 시스템 기획 | Cold-start 상황 크롤링 데이터 기반 추천 설계 | UX/HMI와 직접 연관 낮음(추천 알고리즘형) | MAU 1,300명, 재방문의사 7.0점 |
| ⑨ 대외활동 — 제주바이오AX해커톤(대상), 가짜연구소 등 | 신규 도메인 빠른 학습·실행 | 낮은 직접 연관, 열정·실행력의 보조 근거 | 대상 수상 |

## 3. 문항별 우선순위

### 자소서2 (차별화된 가능성 경험 + 성장) — 메인 소재 선정이 핵심

| 순위 | 소재 | 선정 이유 |
|---|---|---|
| **1순위** | ① 마인드로직 AI챗봇 UX상호작용개선 | 가장 최근 경력, 가장 명확한 정량 성과(3개 지표), JD의 "사용자 시나리오 설계→평가기준 수립→검증→개선"이라는 업무 흐름을 그대로 재현. AB test라는 **실험 설계 역량**까지 증명되어 "가능성"이라는 문항 취지에 가장 부합 |
| 2순위(백업) | ③ 오비이랩 측정SW 사용성개선 또는 ④ 노인사용자 과제추가 | 인터뷰 기반 사용자 리서치라는 더 "교과서적인" 사용성평가 방법론. 1순위 소재가 면접에서 이미 소진되었거나, 더 인간공학적 색채가 필요할 때 대체 |
| 3순위(백업) | ⑥ 볼트업 홈화면 충전구역 추천 고도화 | 현재 재직 중 최신 사례라는 신뢰도는 있으나, 상품성평가보다 추천시스템 최적화에 가까워 결이 다소 어긋남 |
| 배제 | ⑦ 카카오T/U+쿠폰, ⑧ 빵그리의오븐 | 리스크관리·추천알고리즘형으로 UX/HMI 평가 문항과 직접 연관이 낮음. 다른 회사·다른 문항(협업, 문제해결)에서는 활용 가치 있음 |

**1,000자 배분 스켈레톤 (① 마인드로직 기준)**
- 문제 상황 (~20%, 200자): 대화 불만족 83%, 원인(대화주제·정보부족)
- 역할·과정 (~40%, 400자): 사용자 실험 설계, 데이터 클러스터링, AB test 설계·운영
- 결과 (~20%, 200자): 만족도 30%↑, linguistic/interaction cue 25%↑, MAU 5,000명
- 성장/회고 (~20%, 200자): "사용자 피드백을 그대로 수용하지 않고 데이터로 비판적으로 검증해야 한다"는 관점 → 이 관점을 차량 상품성평가에 적용하겠다는 한 문장으로 JD와 연결

### 자소서1 (지원동기 + 입사 후 포부) — 방향성 중심, 경험은 짧게 인용만

| 순위 | 소재 | 역할 |
|---|---|---|
| 1순위 | ② 석사 논문(HMI 연구) | "왜 인간공학을 공부했고, 왜 이 방향을 택했는가"의 학문적 뿌리 — 1~2문장으로 배경만 |
| 2순위 | ① 마인드로직(짧은 인용) | 자소서2에서 깊게 다루므로 여기서는 "실무에서도 같은 방법론을 검증했다" 정도로 한 문장 인용, 중복 서술 금지 |
| 보조 | ⑨ 대외활동(해커톤 대상 등) | 새로운 도메인에 뛰어드는 실행력의 근거로 1문장, 있어도 되고 없어도 됨 |

**1,000자 배분 스켈레톤**
- 도입 (~15%, 150자): SDV·자율주행 전환기의 현대차 + "사람과 기계의 상호작용을 다루는 일"이라는 개인 정체성이 만나는 지점
- 지원동기 (~35%, 350자): 인간공학·HCI 학문적 배경(②) → 실무 검증(① 짧게 인용) → 자동차 HMI로 확장하고 싶다는 논리, 직급이 아니라 이 업무를 택한 이유
- 입사 후 포부 (~40%, 400자): JD 원문 키워드(Agentic AI, Lv.2+/Lv.4 자율주행 기반 심리스 UX, OTA 기반 지속개선 프로세스) 활용해 구체적 미래상 제시
- 마무리 (~10%, 100자): 각오

## 4. 교차 점검 체크리스트

- [ ] 자소서1·2에 동일 프로젝트가 깊게 중복 서술되지 않았는지 확인
- [ ] 자소서2는 반드시 수치 3개 이상 포함(문제 진단 수치 1개 + 결과 수치 2개 이상)
- [ ] 자소서1의 "입사 후 포부"는 JD 원문 표현을 최소 1개 이상 그대로 인용해 구체성 확보
- [ ] 두 문항 모두 "차량 총합 상품성 평가" 트랙임을 문맥상 분명히 하되, 문항 성격상 직접 언급이 어색하면 생략 가능
- [ ] 1,000자는 공백 포함 기준인지 사전 확인(플랫폼마다 상이) 후 글자수 배분 재조정
