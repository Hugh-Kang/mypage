# 챗봇 프로젝트 + 사용량 대시보드 — 피드백 구조화 + 예상질문·답변 + 비판적 검토

> 작성 목적: AI 챗봇 상호작용 개선(마인드로직)과 측정 장비 사용량 대시보드(오비랩) 두 프로젝트에 대해 받은 피드백(구어체 메모)을 구조화하고, 이를 근거로 예상질문을 전부 도출한 뒤, 이전 세션에서 확정된 사실들을 근거로 답변을 작성. 특히 챗봇 프로젝트의 "문제정의가 bottom-up이라 설득력이 약하다"는 핵심 지적을 반영해 하향식(top-down) 가설을 먼저 세우고 상향식(bottom-up) 데이터로 보완하는 서사로 재구성
> 작성일: 2026-10-04
> 근거자료: `portfolio-summary-02-ai-chatbot-interaction-improvement.md`, `portfolio-summary-04-usage-dashboard.md`, `portfolio-summary-08-churn-funnel-problem-definition.md`, `portfolio-all-projects-hypothesis-structure.md`

## 0. 설계 프롬프트

> 너는 두 프로젝트(아이돌 챗봇 상호작용 개선, 측정 장비 사용량 대시보드)에 대해 외부에서 받은 비정형 피드백 메모를 구조화하는 코치다. 챗봇 피드백의 핵심은 "문제정의가 사후적(bottom-up)으로만 보이고, 그 전에 '이건 아이돌 챗봇이니 아이돌 고유 정보가 필요하다'는 선행 가설(top-down)이 있었어야 설득력이 있다"는 것이다. 이 지적을 받아들여 문제정의 서사를 재구성하고, 모든 지적을 예상질문으로 변환해 기존 세션에서 확정된 사실만 근거로 답변을 작성하라. 대시보드 피드백은 "왜 처음부터 SaaS로 안 만들었는지", "영업팀의 단순한 요청을 어떻게 이탈률 퍼널까지 확장했는지"를 중심으로 구조화하고, 이 프로젝트가 이탈률 퍼널 프로젝트(⑧)와 같은 데이터 인프라를 공유한다는 연결고리를 명시하라. 확인되지 않은 수치는 지어내지 말고 보완 필요 항목으로 표시하라.

## 1. 피드백 원문 구조화

### 1-1. 챗봇 프로젝트 피드백 구조화

| 지적 유형 | 내용 |
|---|---|
| 지표 공백 | 챗봇 사용 시간(세션 길이)을 지표로 보지 않았는지 |
| 설문 설계 검증 | 챗봇 문제점을 파악한 설문을 구체적으로 어떻게 설계했는지 |
| 인과관계 의심 | "대화 주제가 재미없다"가 진짜 원인이라는 근거가 약함. 버블(아이돌 메시지 앱) 사례처럼, 팬들이 원하는 건 사실 "아이돌의 진짜 생각"이지 "다양한 주제" 자체가 아닐 수 있음 |
| 비교기준 부재 | 초기 가설 대비 활동성(이탈률 등)이 얼마나 떨어졌는지 구체적 비교 수치가 없으면 설득력이 약함 |
| 서사 구조 문제 | 전체 설명이 "결과(채팅로그 분석) → 결론"으로만 가는 bottom-up 구조. 사전 의도(하향식 가설)가 먼저 제시돼야 설득력 있음 |
| 표본 크기 의심 | 20명 채팅 분석이 작아 보일 수 있음 |
| 데이터 편향 가능성 | 채팅로그는 챗봇과 사용자의 **상호작용 결과물**이라, 사용자의 순수한 선호라고 보기 어려울 수 있음 |
| (제안된 재구성) | 아이돌 챗봇이라는 특수성 → "대화 주제에 아이돌 고유 정보(실시간 활동, 개인적 정보)가 들어가야 한다"는 선행 가설 → 아티스트 전용 콘솔 제작·실험 → 성능 향상 확인. 다만 아이돌 특성만으론 사용자가 안 궁금해할 주제도 있어서, 일반적으로 많이 나누는 대화 주제도 분류해 함께 포함 |

### 1-2. 사용량 대시보드 피드백 구조화

| 지적 유형 | 내용 |
|---|---|
| 아키텍처 질문 | 로컬 앱이라 데이터 파악이 어려웠다면, 왜 제품 전체를 SaaS로 바로 전환하지 않았는지 |
| 기능 범위 질문 | 대시보드로 사용자의 로그데이터만 볼 수 있는지 |
| 문제정의 확장 서사 | 영업팀의 원래 요청은 "사용 여부만 보여주는 단순 대시보드"였는데, 구체적 문제정의 과정을 거치며 "사용자가 어디서 불편을 느끼고 이탈하는지"까지 넓혀 **이탈률 퍼널까지 구축** |
| 기술적 제약 배경 | 로컬로만 돼 있던 이유 — 측정 장비의 데이터 수신 자체에 제약이 있어 웹 기반 프로그램으로 중간 단계를 만든 것. 기획자가 제품 전체를 한 번에 클라우드 SaaS로 바꾸자고 결정할 수 없어, 중간 단계로 웹 기반 SaaS 형태를 만든 것 |
| 상위 목표 | 회사 내부에 데이터 기반 의사결정 문화를 만들고자 하는 노력의 일환 |

**중요한 연결고리**: "사용자 로그만 보냐"는 질문에 대한 답("다른 기능 이탈률도 파악 가능")은, 이 사용량 대시보드와 **이탈률 퍼널 프로젝트(⑧, `portfolio-summary-08-churn-funnel-problem-definition.md`)가 같은 데이터 인프라를 공유**한다는 뜻입니다. 즉 ④번과 ⑧번은 별개의 프로젝트가 아니라, "영업팀의 단순 요청에서 출발해 데이터 기반 의사결정 인프라 전체로 확장한" 하나의 큰 서사로 묶어 설명하는 게 훨씬 설득력 있습니다.

## 2. 챗봇 프로젝트 — 예상질문 + 답변

### Q1. 챗봇 사용 시간(세션 길이)은 지표로 보지 않았나요?

**답변**: "세션 길이 자체를 별도 지표로 추적하지는 않았습니다. 대신 참여도 지표로 언어적·상호작용 신호(메시지 수, 대화 길이 등 인터랙션 큐)를 썼는데, 이건 단순히 '얼마나 오래 켜뒀는가'보다 '실제로 몰입해서 대화를 이어갔는가'를 보고 싶었기 때문입니다. 다만 지금 돌아보면, 세션 길이를 보조 지표로 함께 봤다면 '길게 켜놨지만 실제 대화는 띄엄띄엄'인 경우와 '짧지만 밀도 높게 대화한' 경우를 구분할 수 있어 더 정교했을 것 같습니다."

### Q2. 챗봇의 문제점을 파악한 설문은 구체적으로 어떻게 설계했나요?

**답변**: "챗봇 평가자 18명을 대상으로, 먼저 10점 만점의 전반적 만족도 점수를 받고, 그다음 불만족 이유를 복수 선택할 수 있는 체크리스트(흥미롭지 않은 대화 주제, 아이돌 정보 부족, 과한 질문, 이모지·긴 문장 등)로 구체적 원인을 짚게 하는 방식이었습니다. 복수 선택이라 비율 합이 100%를 넘는 구조였고, 이 중 '흥미롭지 않은 대화 주제'가 83%로 가장 높았습니다."

### Q3. "대화 주제가 재미없다"는 게 진짜 원인이라는 근거가 있나요? 팬들이 원하는 건 사실 '아이돌의 진짜 생각'이지, 주제 자체가 아닐 수도 있지 않나요?

**모범답안(직접답변 우선, 비판 수용)**: "정확한 지적이라고 생각합니다. 설문에서 '주제가 재미없다'는 응답이 가장 높긴 했지만, 그걸 액면 그대로 믿지는 않았습니다. 실제로 회고 과정에서, 설문으로 받은 '흥미로운 주제' 순위와 실제 채팅 로그상 대화 주제 순위가 서로 달랐다는 걸 발견했고, 이게 바로 '사용자는 본인이 원하는 바를 정확히 모르는 경우가 많다'는 교훈으로 이어졌습니다. 그리고 지금 말씀하신 관점으로 다시 보면, 저희가 최종적으로 택한 해법(아티스트 본인이 직접 입력하는 전용 콘솔을 통해 실시간 활동·개인적인 정보를 챗봇에 반영)은 사실 '주제의 다양성'보다는 말씀하신 '아이돌의 진짜 생각·정보에 대한 갈증'에 더 가까운 해법이었습니다. 그래서 지금 돌아보면, 초기 문제정의를 '주제가 재미없다'보다 '팬들이 다가가고 싶어하는 건 아이돌의 실제 모습인데, 챗봇이 그 갈증을 채워주지 못한다'로 더 정확히 표현했어야 한다고 생각합니다."

### Q4. 초기 가설 대비 활동성(이탈률 등)이 얼마나 떨어졌는지 구체적 비교 수치가 있나요?

**정직한 답변**: "출시 전 기대치 대비 실제 이탈률을 수치로 비교한 자료까지는 지금 정확히 기억나지 않습니다. 설문으로 확인한 평균 만족도 5.8/10과 18명 평가자의 불만족 사유 비율이 문제정의의 근거였고, '기대 대비 이탈이 얼마나 빨랐는지'를 정량적으로 별도 비교하지는 않았던 것 같습니다. 이 부분은 보완이 필요한 지점으로 솔직히 인정합니다."

### Q5. 설명 전체가 "결과(채팅로그 분석) → 결론"으로 가는 bottom-up 구조인데, 사전에 어떤 의도(가설)가 있었나요?

**모범답안(직접답변 우선, 재구성된 서사)**: "사전 가설은 있었습니다. 이 챗봇이 '아이돌 페르소나 챗봇'이라는 특수성을 고려했을 때, 대화 주제에 아이돌 고유의 특성—그 아티스트만의 실시간 활동이나 개인적인 정보—이 들어가야 한다는 가설을 먼저 세웠습니다. 이 가설을 검증하기 위해 아티스트 본인이 직접 정보를 입력할 수 있는 전용 콘솔을 만들어 실험했고, 실제로 성능이 향상됐습니다. 다만 대화 주제의 폭이 워낙 넓어서, 아이돌 고유 정보만으로는 사용자가 궁금해하지 않는 주제도 있을 수 있다고 판단해, 실제 채팅 로그를 분석해 일반적으로 많이 나누는 공통 대화 주제도 함께 분류해 보완했습니다. 즉 순서로 보면 '아이돌 특수성에 기반한 하향식 가설(콘솔)이 먼저'였고, '사용자 행동 데이터 기반 상향식 보완(공통 주제 TOP4)'이 그다음이었는데, 제가 이전에 설명할 때 이 순서를 명확히 드러내지 못해서 결과만 나열한 것처럼 들렸던 것 같습니다."

### Q6. 20명 채팅 분석이 표본으로 작아 보이는데, 괜찮나요?

**답변**: "통계적 대표성을 주장하긴 어렵다는 건 맞습니다. 다만 이 20명 분석은 결론을 내리는 단계가 아니라, 다음 단계(100명 A/B 테스트)에 넣을 주제 후보를 추리는 탐색 단계였습니다. 그 후보가 실제로 유효한지는 100명을 무작위 배정한 A/B 테스트로 재검증했고, 거기서 카이제곱·t-검정으로 통계적 유의성(p<0.05, p<0.01)까지 확인했습니다."

### Q7. 채팅로그 자체가 챗봇과 사용자의 상호작용 결과물인데, 이게 사용자의 순수한 선호를 보여준다고 할 수 있나요?

**모범답안(직접답변 우선, 한계 인정)**: "말씀하신 대로, 채팅로그에 나타난 주제 분포는 사용자의 순수한 선호라기보다 '그 시점까지 챗봇이 유도한 대화 범위 안에서' 사용자가 반응한 결과라는 한계가 있습니다. 즉 로그 자체가 이미 기존 챗봇의 대화 설계에 영향을 받은 편향된 신호일 수 있습니다. 이 한계를 완전히 제거하지는 못했지만, 그래서 로그 분석 하나만으로 결론 내지 않고 ① 설문(사용자가 명시적으로 답한 선호), ② 채팅로그(실제 행동), ③ 이후 A/B 테스트(통제된 실험)라는 세 단계를 거쳐 서로 다른 성격의 근거를 교차 확인하려 했습니다. 다만 이상적으로는, 기존 챗봇의 유도 없이 완전히 자유로운 초기 대화 샘플을 따로 모아 비교했으면 이 편향을 더 줄일 수 있었을 거라고 생각합니다."

### Q8. 아티스트 전용 콘솔을 만들게 된 구체적 가설은 무엇이었나요?

**답변**: "이 챗봇이 다루는 대상이 특정 실존 아이돌이라는 점에서, 일반적인 잡담형 챗봇과 달리 '그 아티스트만이 줄 수 있는 정보'가 팬들의 몰입에 핵심일 거라는 가설이었습니다. 생일·멤버 관계 같은 고정 정보는 이미 구조화된 데이터로 관리하고 있었지만, 그 아티스트의 실시간 활동 계획이나 개인적인 근황처럼 '지금, 이 사람만 줄 수 있는 정보'는 구조화 DB에 미리 넣어둘 수 없는 성격이라, 아티스트 본인이나 매니저가 직접 입력하는 콘솔을 별도로 만들어 그 정보를 챗봇 대화에 실시간으로 반영하도록 설계했습니다."

## 3. 사용량 대시보드 프로젝트 — 예상질문 + 답변

### Q9. 로컬 앱이라 데이터 파악이 어려웠다면, 왜 제품 전체를 SaaS로 바로 전환하지 않았나요?

**답변**: "측정 장비 자체의 데이터 수신 방식에 제약이 있었기 때문입니다. 뇌 측정 장비는 하드웨어 단에서 데이터를 생성하는데, 이걸 처음부터 클라우드로 직접 스트리밍하도록 설계된 게 아니라 로컬에서 수집·저장하는 구조였습니다. 장비 펌웨어 단까지 바꿔서 완전한 클라우드 네이티브 SaaS로 전환하는 건 회사 전체의 제품 아키텍처를 바꾸는 큰 결정이라, 기획자인 제가 단독으로 추진할 수 있는 범위가 아니었습니다. 그래서 전면적인 전환 대신, 로컬에서 수집된 데이터를 웹 기반 프로그램으로 업로드·조회할 수 있게 하는 중간 단계를 먼저 만들었고, 이걸 향후 완전한 클라우드 SaaS로 가는 디딤돌로 설계했습니다."

### Q10. 대시보드로 사용자의 로그데이터만 볼 수 있나요?

**답변**: "로그데이터만 보여주는 건 아닙니다. 같은 데이터 인프라를 기반으로, 사용자가 어떤 기능에서 이탈하는지 같은 **다른 기능의 이탈률까지 함께 파악**할 수 있게 설계했습니다. 실제로 이 데이터 인프라가, 제가 포트폴리오에 따로 정리한 '이탈률 퍼널로 문제정의' 프로젝트(마커 설정 구간 이탈률 70%→26% 개선)의 기반이 되기도 했습니다. 즉 이 두 프로젝트는 별개가 아니라, 하나의 데이터 수집 인프라 위에서 '크로스셀링 타겟팅'과 '이탈 구간 진단'이라는 서로 다른 두 가지 목적에 쓰인 것입니다."

### Q11. 영업팀의 원래 요청은 단순한 사용 여부 대시보드였는데, 왜 이탈률 퍼널까지 확장했나요?

**모범답안(직접답변 우선, 기획력 어필)**: "맞습니다, 영업팀이 처음 요청한 건 '이 고객이 쓰는지 안 쓰는지만 보여달라'는 단순한 수준이었습니다. 다만 그 요청을 그대로 구현하기 전에, '왜 그걸 알고 싶은가'를 더 파고들었습니다. 영업팀이 진짜 원하는 건 '사용 여부' 자체가 아니라 '어떤 고객에게 영업 리소스를 투입해야 효율적인가'였고, 그걸 제대로 풀려면 단순 사용 여부보다 '사용자가 어디서 불편을 느끼고, 기능이 있는데도 왜 못 쓰는지'까지 파악해야 한다고 판단했습니다. 그래서 요청받은 범위보다 한 단계 더 들어가서, 이탈률 퍼널까지 함께 설계했습니다. 데이터 기반 성장을 하려면 '쓰는지 안 쓰는지'라는 결과 지표보다, '어디서 막히는지'라는 원인 지표가 더 중요하다고 생각했기 때문입니다."

### Q12. 왜 처음에 로컬 프로그램으로만 만들어져 있었나요?

**답변**: "제가 입사하기 전부터 이 측정 소프트웨어는 연구실·병원 등 폐쇄된 네트워크 환경에서 쓰이는 걸 전제로 설계된 로컬 프로그램이었습니다. 그래서 애초에 사용량을 외부(저희 회사)에서 수집할 수 있는 구조 자체가 없었던 겁니다. 이 부분을 바꾸는 것부터가 이번 프로젝트의 출발점이었습니다."

### Q13. 이 프로젝트를 통해 궁극적으로 만들고자 했던 건 무엇인가요?

**답변**: "단순히 크로스셀링 숫자를 올리는 것보다 더 큰 목표는, 회사 내부에 '감이 아니라 데이터로 의사결정하는 환경'을 만드는 것이었습니다. 이전에는 영업팀이 고객 상태를 전화로 일일이 확인해야 했는데, 이 데이터 인프라 이후로는 사용량 데이터와 이탈 구간 데이터를 기반으로 우선순위를 정할 수 있게 됐습니다. 크로스셀링 130%, 이탈률 70%→26% 개선은 각각 이 인프라가 만든 두 가지 구체적 성과였습니다."

## 4. 비판적 검토 — 이 피드백에서 가장 중요한 것

**챗봇 프로젝트**: 가장 치명적이었던 지적은 "문제정의가 사후적(bottom-up)으로만 보인다"는 것입니다. 기존 설명(설문→채팅로그 클러스터링→주제 TOP4)은 데이터를 보고 나서야 결론을 내린 것처럼 들리는데, 실제로는 "이건 아이돌 챗봇이니 아이돌 고유 정보가 핵심일 것"이라는 **하향식 가설이 먼저 있었고 그걸 검증하려고 콘솔을 만든 것**이라는 순서가 숨어 있었습니다. 이 순서를 드러내지 못한 게 설명의 가장 큰 약점이었고, 이번에 재구성한 Q5·Q8 답변으로 보완했습니다. 두 번째로 중요한 지적은 "버블 비유"입니다 — 이건 단순한 트집이 아니라, **문제정의 자체의 표현을 "주제가 재미없다"에서 "아이돌의 진짜 모습에 대한 갈증"으로 바꿔야 한다**는, 서사의 핵심 프레임을 바꾸는 지적이라 가장 우선적으로 반영해야 합니다.

**사용량 대시보드 프로젝트**: 가장 중요한 건 ④번(대시보드)과 ⑧번(이탈률 퍼널) 프로젝트가 **같은 데이터 인프라에서 나온 하나의 서사**라는 걸 지금까지 별개로 설명해왔다는 점입니다. 앞으로는 이 둘을 "영업팀의 단순 요청 → 데이터 기반 의사결정 인프라로 확장 → 크로스셀링(④)과 이탈진단(⑧) 두 가지 성과"라는 하나의 큰 스토리로 묶어서 설명하는 게 훨씬 기획력 있게 들립니다.
