# 티빙 임직원용 데이터 추출/정책 확인 챗봇 — 처음부터 설계하는 답변

## 0. 설계 프롬프트

> 너는 티빙 내부 임직원(데이터 담당자, 기획자, CS 등)이 자연어로 데이터를 추출하거나 사내 정책을 확인할 수 있는 챗봇을 처음부터 설계해야 하는 PM이다. 이건 팬/시청자용 콘텐츠 추천 챗봇과는 목적이 다르다는 것을 먼저 인지하고 — 자연스러움보다 정확성·권한 통제·감사 가능성이 훨씬 중요하다는 것 — 이 차이를 반영한 설계를 개요/문제정의/목적/데이터/분석내용(설계절차)/통찰/기대효과/의의로 구조화하라. 최근 개인정보 유출 이슈가 있었던 회사라는 맥락도 자연스럽게 녹여라.

## 1. 개요

티빙 임직원이 SQL을 직접 짜거나 정책 문서를 뒤지지 않고도, 챗봇에게 자연어로 물어 데이터를 추출하거나 사내 시스템 정책을 확인할 수 있는 내부용(사내) AI 에이전트를 설계하고 싶습니다.

## 2. 문제정의

두 가지 축의 문제가 있습니다. 첫째, **데이터 추출**은 비개발 직군 임직원이 특정 지표를 확인하려면 매번 데이터팀에 요청하고 기다려야 하는 병목이 있거나, SQL을 직접 짤 줄 알아야 하는 진입장벽이 있습니다. 둘째, **시스템 정책**은 여러 문서·위키·슬랙 공지에 흩어져 있어 최신 정책을 찾는 데 시간이 걸리고, 담당자가 바뀌면 그 지식 자체가 유실되는 문제가 있습니다.

## 3. 목적

데이터 추출 요청의 리드타임을 줄이고, 정책 관련 질문에 항상 최신이고 정확한 답을 제공해서 반복적인 데이터팀 요청·CS 부담을 줄이는 것이 목적입니다.

## 4. 활용할 데이터

| 데이터 유형 | 내용 | 활용 목적 |
|---|---|---|
| DB 스키마 메타데이터 | 테이블/컬럼명과 설명(스키마 온톨로지) | 자연어 질문을 SQL로 변환(Text-to-SQL)할 때 참조 |
| 정책 문서(위키·노션·슬랙 공지) | 임베딩해서 벡터DB에 저장 | 정책 질의에 RAG(검색 후 생성) 방식으로 답변 |
| 임직원 권한 정보(일반DB) | 직급·팀별 접근 가능 테이블/컬럼 범위 | 사용자 권한 밖의 데이터는 애초에 조회 불가하도록 통제 |
| 쿼리·질의 감사 로그 | 누가 언제 어떤 데이터를 조회했는지 | 데이터 거버넌스·사후 추적 |

## 5. 분석 내용 (설계 절차)

먼저 질의 의도를 "데이터 추출 요청"과 "정책 확인 요청"으로 분류해서 라우팅합니다.

**데이터 추출 요청**이면, 사용자의 자연어 질문을 스키마 메타데이터를 참조해 SQL로 변환합니다. 이때 **사용자의 권한을 먼저 확인해서, 접근 가능한 테이블·컬럼으로만 쿼리 범위를 제한**합니다. 생성된 SQL을 검증 없이 곧바로 실행하지 않고, 쿼리 내용이나 결과 요약을 함께 보여줘서 사용자가 결과를 한 번 더 확인할 수 있게 설계합니다. 자동 생성된 SQL이 틀렸을 때 잘못된 숫자가 그대로 의사결정에 쓰이는 위험을 막기 위한 최소한의 안전장치입니다.

**정책 확인 요청**이면, 벡터DB에 임베딩된 정책 문서에서 관련 내용을 검색해(RAG) 그 내용을 근거로 답변을 생성합니다. 이때 **답변과 함께 원본 문서 링크를 항상 같이 제공**해서, 챗봇의 요약만 믿지 않고 원본을 확인할 수 있게 합니다.

모든 질의·응답은 감사 로그로 남겨, 누가 언제 어떤 데이터를 조회했는지 추적할 수 있게 합니다.

## 6. 통찰

팬·시청자용 챗봇은 "자연스러움"이 중요하지만, 내부용 챗봇은 **"정확성과 통제 가능성"**이 훨씬 중요하다는 것이 핵심 통찰입니다. 특히 SQL 자동 생성처럼 틀리면 잘못된 숫자가 그대로 의사결정에 쓰일 수 있는 영역은, 완전 자동화보다 "제안 후 확인" 구조가 안전합니다. 이건 이전에 정리한 "사실 기반 정보는 구조화된 근거로 답한다"는 할루시네이션 관리 원칙과 같은 철학이지만, 내부용에서는 **권한 관리와 감사 로그**라는 요소가 추가로 필요합니다. 특히 최근 개인정보 유출 이슈를 겪은 회사인 만큼, 내부 챗봇이 오히려 새로운 데이터 유출 경로가 되지 않도록 권한 통제와 감사 로그를 설계 초기 단계부터 반드시 포함해야 한다고 생각합니다.

## 7. 기대 효과

- 데이터팀에 요청하고 기다리는 대신 셀프서비스로 리드타임 단축
- 정책 문의로 인한 반복 CS·데이터팀 부담 감소
- 감사 로그를 통한 데이터 거버넌스 강화 — 특히 민감 데이터 접근 이력 추적 가능

## 8. 의의

외부 사용자용 챗봇과 내부 임직원용 챗봇은 목적(자연스러움 vs 정확성·통제)이 근본적으로 다르므로 설계 원칙도 달라야 한다는 것을 보여주는 답변입니다. Discovery팀의 "AI 챗봇 에이전트"가 반드시 시청자 대상만을 의미하지 않을 수도 있다는 폭넓은 이해를 보여줄 수 있고, 특히 보안·거버넌스에 대한 인식을 함께 어필할 수 있는 답변이라고 생각합니다.
