# 포트폴리오 프로젝트 요약본 ⑥ — 언어 패키지로 협업 환경 구축 (마인드로직)

> 작성 목적: 포트폴리오 9개 프로젝트 요약 작업의 여섯 번째. 요청대로 1분 요약 스크립트를 두괄식(결론·핵심 구조 먼저)으로 작성. 이 프로젝트는 다른 8개와 달리 **결과가 숫자로 정량화되지 않은 유일한 프로젝트**라는 점을 스스로 먼저 짚고, 번역 품질 검증 여부가 불명확하다는 점(이미 `mindlogic-chatbot-llm-rag-architecture-inference.md`에서 확인된 한계)도 반영
> 작성일: 2026-10-02
> 근거자료: `portfolio-all-projects-hypothesis-structure.md`(포트폴리오 원문 구조화), `mindlogic-chatbot-llm-rag-architecture-inference.md`(번역 검증 불명확 지점)

## 0. 설계 프롬프트

> 너는 지원자의 포트폴리오 프로젝트 "언어 패키지로 협업 환경 구축"을 면접에서 바로 설명할 수 있는 요약본으로 만드는 코치다. 1분 요약 스크립트는 반드시 두괄식으로 — "무엇을 만들었고, 핵심 구조가 뭐고, 결과가 어땠는지"를 먼저 말한 뒤 세부 배경으로 들어가는 순서로 작성하라. 이 프로젝트는 포트폴리오 9개 중 유일하게 결과가 숫자로 정량화되지 않았다는 걸 숨기지 말고 먼저 짚고, 그 이유에 대한 답변까지 준비하라. 또한 OpenAI API로 자동 번역한 중국어·일본어의 품질을 실제로 검증했는지는 포트폴리오에 명시돼 있지 않다는 점(이미 다른 문서에서 확인된 한계)을 정직하게 반영하라.

## 1. 1분 요약 스크립트 (두괄식)

> "저는 화면 문구를 개발자가 매번 코드로 수정하던 방식을, 구글 스프레드시트 기반 key-value 협업 환경으로 바꿔서, 비개발 직군도 추가 개발 공수 없이 문구를 직접 수정·배포할 수 있는 구조를 만들었습니다. 구조는 이렇습니다 — 구글 스프레드시트에 페이지별 key-value 텍스트를 언어별로 입력하면 JSON으로 저장되고, 개발 스크립트가 이를 import해 화면에 그대로 반영합니다. 한국어·영어만 입력해도 OpenAI API로 중국어·일본어가 자동 번역되고, 변동이 생기면 Make로 담당자에게 Slack 알림이 갑니다. 그 결과 해외 협력팀 4인과 내부 10인 사이의 문구 관련 커뮤니케이션 비용을 줄였습니다. 다만 이 프로젝트는 다른 프로젝트들과 달리 그 효과를 구체적인 숫자(예: 절감된 시간)로 정량화하지는 못했다는 한계가 있습니다."

## 2. 구조화 (문제정의 → 가설 → 방법론 → 결과 → 회고)

| 단계 | 내용 |
|---|---|
| 문제정의 | 화면 문구가 빈번히 바뀔 때마다 스크립트 수정에 격주로 2시간 이상 소요. 해외 시장 출시 예정이라 한·중·영 다국어 문구 작성 환경 필요 |
| 가설 | 화면 문구를 구글 스프레드시트 기반 key-value 협업 환경으로 옮기면, 개발 공수 없이 문구를 수정·배포할 수 있어 협업 비용이 줄어들 것이다 |
| 방법론 | 구글 스프레드시트에 페이지별 key-value 텍스트를 언어별 입력 → submit 시 JSON 저장 → 개발 스크립트가 import해 key-value 기준 localize → OpenAI API로 한·영 입력 시 중·일 자동번역 → Make로 변동 발생 시 담당자 Slack 알림 |
| 결과 | 구글시트에서 누구나 문구 직접 수정 가능, 추가 개발 공수 없이 배포 시 자동 적용, 해외 협력팀 4인·내부 10인 커뮤니케이션 비용 절감 **(단, 숫자로 정량화된 지표는 없음)** |
| 회고(포트폴리오 원문) | 명시적 회고 없음 |

## 3. 핵심 꼬리질문 1 — "다른 프로젝트들은 다 숫자(%, 건수, MAU)가 있는데, 이 프로젝트만 '커뮤니케이션 비용 절감'이라는 정성적 표현만 있습니다. 왜 정량화하지 못했나요?"

**모범답안(직접답변 우선, 스스로 먼저 인정)**: "맞습니다, 이 프로젝트는 제 포트폴리오 9개 중 유일하게 정량적 성과가 없습니다. 이유는, 이 프로젝트의 효과가 '문구 수정에 걸리는 시간'이나 '개발자 리소스 투입량'처럼 측정 가능한 지표였는데, 당시엔 개선 전 상태(격주 2시간이라는 수치)만 문제 인식 단계에서 확인했고, 개선 후에 그 시간이 실제로 얼마나 줄었는지를 별도로 추적하지 않았기 때문입니다. 지금 다시 한다면, 문구 수정 요청 건수와 처리 소요 시간을 도입 전후로 비교해서, '개발자 공수 투입 시간이 몇 % 줄었는지'를 정량 지표로 반드시 남겼을 것 같습니다. 이건 제가 스스로 인정하는 이 프로젝트의 가장 큰 보완점입니다."

## 4. 핵심 꼬리질문 2 — "OpenAI API로 자동 번역한 중국어·일본어, 품질은 어떻게 검증했나요?"

**모범답안(직접답변 우선, 정직한 경계)**: "솔직히 말씀드리면, 번역 결과를 사람이 사후에 점검하는 구체적인 절차까지는 제가 정확히 기억하거나 기록해두지 못했습니다. 다만 구조상 이 번역은 실시간 사용자 대화가 아니라 화면 문구라는, 비교적 짧고 반복적인 텍스트였기 때문에 담당자가 스프레드시트에서 결과를 바로 눈으로 확인할 수 있는 환경이긴 했습니다. 다시 설계한다면, 자동 번역된 결과도 배포 전에 원어민 검수나 최소한의 샘플 검수 단계를 거치는 절차를 공식적으로 넣고 싶습니다."

## 5. 그 외 예상 꼬리질문 2가지

### 5-1. "왜 전문 번역 관리 툴이나 i18n 전용 솔루션을 쓰지 않고 구글 스프레드시트로 직접 만들었나요?"

**모범답안**: "스타트업 환경에서 전문 번역 관리 툴을 도입하려면 비용과 도입 시간이 들었는데, 당장 급한 건 '비개발자가 개발자 없이도 문구를 바로 고칠 수 있게 하는 것'이었습니다. 이미 모두가 익숙하게 쓰던 구글 스프레드시트를 활용하면 별도 학습 비용 없이 바로 쓸 수 있었고, JSON 변환·자동 번역·Slack 알림 정도의 자동화만 추가로 연결하면 충분히 문제를 해결할 수 있다고 판단해서, 복잡한 전용 툴보다 가벼운 자체 구축을 택했습니다."

### 5-2. "Make로 Slack 알림을 준다고 했는데, 그 알림은 실제로 어떤 문제를 막기 위한 거였나요?"

**모범답안**: "문구가 스프레드시트에서 바뀌어도, 그 변경이 실제로 서비스에 반영됐는지 담당자가 놓치면 '수정했다고 생각했는데 반영이 안 된' 상태로 남을 위험이 있었습니다. 그래서 변동이 발생하면 자동으로 담당자에게 알림을 줘서, 수정과 반영 사이의 공백을 눈으로 바로 확인할 수 있게 한 것이었습니다."
