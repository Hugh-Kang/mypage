# "추천 모델 PRD는 기획자로서 어떻게 작성해야 할까" — 답변 정리

> 작성 목적: 추천 모델 PRD 작성 방법론에 대한 질문에 두괄식으로 답할 수 있도록 프레임워크와 실제 경험 연결을 정리 — 실제 2차 면접 Q12(PRD 작성 내용)에 대한 심화 보완
> 작성일: 2026-10-21
> 근거자료: `tving-2nd-interview-actual-2026-10-20-structured.md` #10~#12, `tving-2nd-interview-cto-answers-critical-review.md`

## 핵심 요약 (두괄식)

추천 모델 PRD에서 기획자가 반드시 정의해야 할 것은 **"모델이 무엇을 할지"가 아니라 "모델을 둘러싼 문제·데이터·정책·검증 기준"**입니다. 모델 자체의 알고리즘 선택은 엔지니어의 전문 영역으로 존중하되, ① 문제정의·목표지표, ② 인풋/아웃풋 명세, ③ 데이터 요구사항과 한계, ④ 정책·비즈니스 룰, ⑤ 실험(AB테스트) 설계, ⑥ 실패 시 폴백 기준, 이 여섯 가지는 기획자가 명확히 정의해야 추천 모델 PRD가 "구현 가능한 문서"가 됩니다.

---

## 추천 모델 PRD 핵심 구성요소

| # | 구성요소 | 기획자가 정의할 내용 |
|---|---|---|
| 1 | 문제정의·목표지표 | 어떤 사용자의 어떤 문제를 풀려는지(예: 콜드스타트 신규 유입자의 선택 피로), 성공을 측정할 1차 지표(CTR·전환율 등)와 상위 비즈니스 지표(구독 유지율·매출)와의 연결 |
| 2 | 타겟 세그먼트 | 전체 사용자 대상인지, 특정 세그먼트(신규/콜드스타트, 헤비유저, 특정 취향군)부터 적용할지 |
| 3 | 인풋/아웃풋 명세 | 모델에 들어가는 입력(사용자 행동 데이터, 콘텐츠 메타데이터)과 출력 형식(추천 리스트 개수, 스코어 유무, 노출 위치)을 명확히 정의 — 어떤 상황에서 어떤 액션이 어떤 아웃풋으로 이어지는지 |
| 4 | 데이터 요구사항과 한계 | 어떤 데이터가 필요하고 현재 무엇이 부족한지(콜드스타트면 대안은 콘텐츠 기반 추천·유사서비스 벤치마킹), 데이터 품질 이슈(크롤링 데이터의 예외처리 등) |
| 5 | 모델 후보 제시(선택은 엔지니어 존중) | 기획자가 후보 모델(예: Word2Vec, 협업필터링 등)을 조사해 제시하되, 최종 모델 선택과 파라미터 튜닝은 AI 엔지니어의 판단을 존중 — 기획자는 "왜 이런 후보를 제시했는지"에 대한 근거(인풋/아웃풋 요구사항과의 적합성)만 명확히 하면 충분 |
| 6 | 정책·비즈니스 룰 | 모델 바깥에서 기획자가 직접 결정해야 하는 영역 — 특정 카테고리 노출 제외, 다양성 보장 규칙, 노출 빈도 제한, 스포일러 필터링 같은 정책성 요구사항 |
| 7 | 실험(AB테스트) 설계 | 실험군·대조군 정의, 샘플 크기, 측정 기간, 1차·2차 지표 |
| 8 | 실패 시 폴백 기준 | 추천 결과가 없거나 품질이 기존보다 떨어질 경우의 대체 로직(예: 인기순 노출로 폴백), 롤백 기준 |

## 실제 경험과 연결

> "저는 건강디저트 추천 플랫폼 PRD를 작성할 때, 콜드스타트 상황이라 사용자 행동 데이터가 없다는 것부터 명시하고, 그래서 1차로는 콘텐츠 기반 추천(상품·리뷰 데이터 기반)으로 시작한다는 점, 찜(좋아요) 이후에는 유사 상품 추천이 필요하다는 인풋/아웃풋 요구사항을 정의했습니다. 모델은 몇 가지 후보(Word2Vec 등)를 제시했지만 최종 선택은 AI 엔지니어분들의 판단을 존중했고, 저는 서비스 정책과 인풋/아웃풋 요구사항을 구체적으로 정의하는 데 집중했습니다."

이 설명은 실제 면접에서 이미 다룬 내용(건강디저트, Word2Vec, "모델 선택은 엔지니어 존중, 정책은 PM이 정의")을 그대로 재사용할 수 있어, 추가로 암기할 내용이 많지 않습니다. 다만 실제 면접 답변에서는 **"실험 설계"와 "실패 시 폴백 기준"**이 빠져 있었으므로, 이번엔 이 두 가지를 추가로 언급하면 훨씬 완성도 높은 답변이 됩니다.

## 예상 꼬리질문

| 꼬리질문 | 대응 방향 |
|---|---|
| 모델 선택까지 PM이 관여하지 않는 이유는? | PM이 모델 내부 구조까지 판단하려 하면 오히려 엔지니어의 전문 영역을 침범해 비효율이 생기고, PM은 "무엇을 입력하고 무엇이 나와야 하는가"라는 요구사항 정의에 집중하는 것이 역할 분담상 더 효율적이라고 설명 |
| PRD에 실험 설계까지 넣어야 하는 이유는? | 추천 모델은 출시 즉시 "정답"이 아니라 가설이므로, PRD 단계에서부터 어떻게 검증할지(AB테스트 설계)를 명시해야 출시 후 바로 효과 측정이 가능하고, 사후에 측정 방법을 급하게 설계하는 비효율을 막을 수 있다고 설명 |
| 폴백 기준을 PRD에 포함하는 이유는? | 추천 모델은 콜드스타트·엣지케이스에서 결과가 없거나 나쁠 수 있는데, 이를 사전에 정의해두지 않으면 장애 상황에서 임기응변으로 대응해야 해 서비스 안정성이 떨어진다고 설명 |
