# "티빙에서 A/B Test 플랫폼을 설계한다면?" — 설계 답변 + 가장 중요하게 보는 것

> 작성 목적: Discovery팀 JD에 명시된 "A/B Test Platform" 모듈에 대한 설계 제안. `tving-discovery-role-priority.md`에서 이미 3순위(가장 약한 근거)로 평가된 영역이므로, "실험 1건을 수행한 경험"과 "여러 팀이 반복적으로 쓰는 플랫폼을 설계하는 것"의 층위 차이를 스스로 인지하고 있다는 걸 답변 안에서 정직하게 드러내면서, 실제 실험 경험에서 얻은 교훈을 플랫폼 설계 원칙으로 일반화
> 작성일: 2026-09-30
> 근거자료: `ab-test-retrospective-key-lessons-answer.md`(실제 A/B 테스트 회고 교훈), `tving-discovery-role-priority.md`(A/B Test Platform 항목의 약점 인식), `home-recommendation-ab-test-fact-resolution.md`(실제 수행한 실험 설계)

## 0. 설계 프롬프트

> 너는 "실험 1건을 직접 수행한 경험"은 있지만 "여러 팀이 반복적으로 쓰는 실험 플랫폼을 설계·운영한 경험"은 없는 지원자다. 이 격차를 숨기지 말고 답변 앞부분에서 정직하게 인지한 뒤, 실제 실험에서 얻은 회고적 교훈(비교가능성, 관련 모집단 한정, 리딩+가드레일 지표 병행)을 "여러 팀이 매번 새로 겪지 않도록 플랫폼이 기본값으로 강제해야 할 것"으로 일반화해서 설계하라. 실험 간 충돌 관리처럼 단일 실험에는 없지만 플랫폼 특유의 문제도 짚어라. 마지막으로 "가장 중요하다고 보는 것" 하나를 명확히 골라라.

## 1. 개요 (및 정직한 전제)

정확히 말씀드리면, 저는 실험 1건을 설계·수행한 경험은 있지만, 여러 팀이 반복적으로 사용하는 실험 "플랫폼"을 직접 설계·운영해본 경험은 없습니다. 다만 그 경험에서 얻은 교훈을 플랫폼 레벨로 일반화해서 답변드리겠습니다.

## 2. 문제정의

여러 팀이 각자 A/B 테스트를 진행하다 보면 같은 실수가 반복될 위험이 있습니다 — 무작위 배정 없이 그냥 전후 비교를 하거나, 표본이 애초에 비교 불가능한 집단이거나, 하나의 지표만 보고 성급하게 결론을 내리는 것입니다. 또한 여러 팀이 동시에 각자 실험을 돌리면, 같은 사용자가 여러 실험에 동시에 배정되어 실험 간 상호작용 효과가 섞이는 문제도 생길 수 있습니다.

## 3. 설계 목적

통계적으로 올바른 실험 설계(무작위 배정, 비교 가능한 집단, 다중 지표 검증)를 각 팀이 매번 새로 고민하지 않고 **플랫폼의 기본값으로 강제**해서, 실험의 질적 편차를 줄이고 신뢰할 수 있는 의사결정을 반복 가능하게 만드는 것이 목적입니다.

## 4. 핵심 구성 요소 — 4단계로 설계

| 단계 | 플랫폼이 제공해야 할 기능 | 왜 필요한가 |
|---|---|---|
| ① 실험 설계 | 가설 등록 폼, 표본 크기·검정력 계산기, 대상 모집단 정의 도구 | 실험을 설계하는 사람이 통계 전문가가 아니어도, "이 정도 표본이면 유의미한 차이를 판별할 수 있는지"를 미리 확인하게 함 |
| ② 배정·실행 | 무작위 배정 엔진(같은 사용자는 항상 같은 그룹에 고정되는 sticky bucketing), 실험 간 트래픽 격리(exclusion group) | 임의로 그룹을 나누는 실수를 방지하고, 여러 실험이 같은 사용자에게 동시에 적용돼 결과가 오염되는 것을 방지 |
| ③ 모니터링·분석 | 실시간 가드레일 지표 대시보드(매출·이탈률 같은 안전 지표가 급격히 나빠지면 자동 알림/조기 중단), 통계적 유의성 자동 계산 | 하나의 리딩 지표(예: CTR)만 보고 성급히 결론 내리지 않도록, 주요 지표와 가드레일 지표를 함께 강제로 보여줌 |
| ④ 거버넌스·기록 | 진행 중인 전체 실험 카탈로그(누가 어떤 실험을 하는지 전사 공유), 실험 설계·결과를 표준 템플릿으로 기록·보관 | 팀 간 실험 충돌을 사전에 인지하게 하고, 나중에 같은 실험을 다시 설명해야 할 때 과정 자체가 기록으로 남아있게 함 |

## 5. 가장 중요하다고 보는 것

네 가지 구성 요소 중 하나만 고른다면, **② 무작위 배정과 실험 간 트래픽 격리를 플랫폼이 자동으로 보장하는 것**이 가장 중요하다고 생각합니다. 표본 크기 계산이나 유의성 검정은 잘못돼도 사후에 재검토하면 바로잡을 수 있지만, **애초에 무작위 배정이 깨지거나 여러 실험이 서로 오염되면, 그 실험 자체가 처음부터 신뢰할 수 없는 데이터를 만들어내기 때문에 사후에 되돌릴 방법이 없습니다.** 즉 플랫폼이 존재하는 가장 근본적인 이유는 "각 팀이 통계를 잘 아느냐"에 의존하지 않고, 가장 치명적이고 되돌릴 수 없는 실수(배정 오염)를 시스템 차원에서 원천 차단하는 것이라고 생각합니다.

## 6. 기대 효과

- 팀마다 실험 품질이 들쭉날쭉해지는 것을 방지하고, 회사 전체의 데이터 기반 의사결정 신뢰도를 높임
- 실험 설계에 드는 반복적인 통계 검토 리소스를 절감
- 실험 카탈로그 공유로 팀 간 중복·충돌 실험을 사전에 조율

## 7. 의의

이 답변은 제가 직접 플랫폼을 만들어본 경험이 아니라, **직접 겪은 실험의 실수 가능 지점들을 플랫폼이 구조적으로 막아주는 방식으로 일반화한 설계**입니다. 실무 경험이 있는 개별 실험 감각을, 여러 팀이 함께 쓰는 시스템 설계로 확장할 수 있다는 것을 보여드리고 싶습니다.
