## 0. 설계 프롬프트

> 너는 방금 공유받은 챗봇·AI 에이전트 개념 레퍼런스 자료를 구조화하는 코치다. 원문의 핵심 논지(동작 원리 차이, 5대 기준, RAG 챗봇의 위치, 에이전트 개수가 성숙도 지표인 이유, 도입 판별 기준, 확장 경로)를 항목별로 정리하라. 그 다음 이 개념을 티빙 Discovery팀의 "AI 챗봇 에이전트" JD 맥락에 적용해서, 실제 면접에서 나올 법한 질문 5개를 뽑아라. 추상적 개념 질문이 아니라, 지원자가 티빙 서비스에 이 개념을 적용해서 답해야 하는 형태로 구성하라.

## 1. 챗봇의 동작 원리와 한계

| 구분 | 동작 방식 | 특징 |
|---|---|---|
| 규칙 기반 챗봇 | 시나리오 트리(사전에 그려둔 분기 흐름)를 그대로 따라감 | 예측 가능, 운영비용 낮음 / 트리에 없는 질문엔 "이해 못함"으로 종료 |
| LLM 기반 챗봇 | LLM이 자연스러운 문장으로 답변 생성 | 표현은 자연스럽지만 여전히 **단일 턴 질의응답**의 반복, 답변 후 실행은 안 함 |

**챗봇의 3가지 근본 한계**: ① 스스로 목표를 세우거나 계획 수정 불가 ② 외부 시스템 접근 도구 없음/극히 제한적 ③ 대화 종료 시 맥락 소멸(연속성 없음)

## 2. AI 에이전트의 동작 원리 — 3단계 루프

1. **목표 분해(Planning)**: 큰 목표를 하위 작업으로 LLM이 실행 시점에 스스로 쪼갬
2. **도구 호출(Tool Use)**: Function Calling으로 어떤 도구를 어떤 인자로 부를지 LLM이 구조화된 형식으로 지정, 결과를 다시 받음
3. **결과 검증과 재시도(Verification Loop)**: 결과를 관찰 → 목표에 비춰 재판단 → 실패 시 조건 변경·재시도

> Anthropic 구분: 사람이 미리 짠 경로대로 LLM+도구를 엮은 것 = **워크플로우** / LLM이 실행 흐름·도구 사용을 직접 통제 = **에이전트**

## 3. 결정적 차이 5가지 (비교표)

| 기준 | 챗봇 | AI 에이전트 |
|---|---|---|
| 자율성 | 없음 — 정해진 시나리오 범위 내 응답 | 높음 — 목표만 주면 실행 경로를 스스로 설계·수정 |
| 도구 사용 | 없거나 고정 1~2개 | 다수 도구를 스스로 선택해 호출 |
| 메모리 | 현재 대화 맥락만, 세션 종료 시 소멸 | 작업 이력·중간결과 저장, 장기 기억 참조 |
| 멀티스텝 추론 | 단일 턴 반복 | 목표 분해 후 여러 단계 순차·반복 실행 |
| 실패 복구 | 없음(오답도 응답으로 종료) | 결과 검증 후 실패 시 재시도·경로 변경 |

- 다섯 기준은 이분법이 아니라 **스펙트럼**(IBM)
- **자율성**이 가장 본질적인 축 — 이 정도를 개념화한 용어가 "Agentic AI"

## 4. RAG 챗봇의 위치 — 챗봇과 에이전트 사이의 중간 지대

- RAG 챗봇 = **"도구를 하나 가진 챗봇"** (검색이라는 고정 도구, 검색 시점도 대개 설계 시 고정)
- 목표 분해·실패 복구 루프 없음, 응답은 여전히 단일 턴 → **도구 사용 기준에서만 반 걸음 에이전트 쪽**
- 실무적 함의: ① "RAG 도입=AI 도입 완료"라는 착오 방지 ② RAG는 에이전트와 경쟁 기술이 아니라 **에이전트가 활용하는 부품**(검색 도구로 재활용 가능)

## 5. 에이전트 개수가 AI 도입 성숙도 척도인 이유

- 에이전트 운영에는 **도구/API 권한, 작업이력 저장소, 실행계층, 관측(Observability), 거버넌스**가 모두 필요 — 챗봇은 이 중 아무것도 없이 시작 가능
- 통계: 조직의 88%가 AI를 쓰지만 전사 확산은 7%, 파일럿 통과도 38% 수준 (McKinsey 2025·Gartner 2024) → "도입 여부"는 더 이상 변별력 없음, "사람 없이 끝까지 도는 업무가 몇 개인가"가 변별점
- **한계비용 논리**: 첫 에이전트 비용 대부분은 공통계층(도구규격·인증·로그·평가셋)에 들어감 → 두 번째부터는 재사용해서 비용 급감 → 개수 증가 = 재사용 가능한 기반이 실제로 만들어졌다는 신호(하나는 프로젝트, 여럿은 플랫폼)
- 개수를 셀 때 **유효 조건 4가지**: ①실제 트래픽 처리 ②자율 완료율 목표치 충족 ③되돌림·승인 경로 정의 ④성과지표(처리시간·건당비용·품질) 연결 — 이 조건 없이 세면 "데모 카운터"에 불과

### 성숙도 단계표

| 단계 | 운영 중인 에이전트 수 | 조직 상태 |
|---|---|---|
| 0·대화 | 0(챗봇·RAG챗봇만) | 답변 자동화까지, 도구/권한 계층 없음 |
| 1·첫 실행 | 1(읽기전용 중심) | 파일럿 1건, 공통계층 없이 개별 구축 |
| 2·재사용 | 2~5 | 도구·인증·관측이 공통계층으로 분리 |
| 3·표준 운영 | 6~20 | 평가·승인·롤백이 표준 절차, 부서 단위 확산 |
| 4·오케스트레이션 | 20+ | 에이전트끼리 위임·협업, 전사 거버넌스 확립 |

## 6. 언제 챗봇, 언제 에이전트인가 — 4가지 판별 질문

1. 정보 제공으로 끝나는가, 시스템 조작까지 필요한가?
2. 처리 경로를 사전에 다 그릴 수 있는가(정형)?
3. 오류의 비용을 감당할 수 있는가(되돌리기 어려운 작업이면 Human-in-the-Loop 필요)?
4. 반복 빈도가 높아 투자 대비 효과가 나오는가?

## 7. 사례로 본 전환 — 고객센터 / 사내 헬프데스크

- **고객센터**: 챗봇(링크 안내만) → 에이전트(배송상태 직접조회+보상쿠폰 발급까지 자동처리, CRM 자동기록). 상담원 역할이 "응답 못한 질문을 받는 사람" → "에이전트 처리 결과를 승인·감독하는 사람"으로 전환
- **사내 헬프데스크**: 챗봇(매뉴얼 링크) → 에이전트(계정상태·로그 조회로 원인 특정, 권한범위 내 잠금해제/초기화 수행, 권한 밖은 티켓 생성)

## 8. 챗봇→에이전트 3단계 확장 경로

| 단계 | 내용 | 산출물(다음 단계 자산) |
|---|---|---|
| 1. 근거 강화 | 챗봇+RAG(사내문서 검색) | 문서 파이프라인, 검색품질 평가기준, 접근권한 체계 |
| 2. 실행 확장 | 읽기 전용 도구 연결(조회형) | 도구 연동 표준 규격 (잘못 실행돼도 데이터 안 바뀜 → 낮은 위험으로 검증) |
| 3. 완결 위임 | 쓰기 도구 + 검증루프 + 사람 승인 | 본격적 에이전트, 앞 단계 자산 재사용 |

**원칙**: 단계를 건너뛰면(1→3) 사고 시 원인 특정이 어려움. 단계마다 검증 관문을 둬서 실패를 국지화해야 함.
